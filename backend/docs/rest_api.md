# Fitness Assistant API — документация

Документация по внешнему REST API сервиса. Полные схемы тел запросов и ответов смотрите
в Swagger — здесь описаны только общие соглашения и специфика запросов по тегам.

**Swagger UI:** <http://94.228.166.134:8181/api/v1/swagger/index.html>

**Base URL:** `/api/v1`

---

## Общие принципы

### JWT авторизация

API использует JWT (JSON Web Token) для авторизации. Токен состоит из трёх частей —
`header.payload.signature`, и в payload есть два типа полей:

- **Публичные (registered) поля** — стандартные поля, определённые спецификацией JWT.
  Сервис использует `exp` (`expiresAt`) — время истечения токена.
- **Приватные (custom) поля** — специфичные для этого API. Сейчас это `userID` —
  идентификатор пользователя, к которому привязан токен.

Приватные поля клиенту разбирать не нужно — они нужны только серверу. Клиент должен
воспринимать токен как непрозрачную строку и просто передавать его в запросах.

### Токены и их использование

При успешной регистрации (`/auth/signup`) или входе (`/auth/login`) сервис выдаёт пару
токенов:

| Токен | Время жизни | Назначение |
| --- | --- | --- |
| `access_token` | 30 минут | Передаётся в защищённых запросах для авторизации |
| `refresh_token` | 10 дней | Используется только для получения новой пары токенов |

Для доступа к защищённым эндпоинтам (например, `GET /users/{id}`) `access_token`
передаётся в заголовке:

```text
Authorization: Bearer <access_token>
```

Часть эндпоинтов использует **опциональную авторизацию** (в документации помечены так):
запрос работает и без заголовка `Authorization` (анонимный режим), а с валидным токеном
дополнительно возвращает данные пользователя. Если заголовок передан, но токен
невалиден или истёк, запрос всё равно завершится ошибкой `401` — он не «молча»
превращается в анонимный.

Когда `access_token` истекает, новую пару токенов нужно получить через
`POST /auth/refresh`, передав текущий `refresh_token` в теле запроса. `refresh_token`
одноразовый: после использования он помечается использованным, и повторно применить его
нельзя — в ответ на такую попытку сервер вернёт ошибку `invalid_token`.

### Параметры запроса

API использует три способа передачи параметров:

- **Path-параметры** — часть пути, например `id` в `/users/{id}`. Обязательны всегда,
  ошибка парсинга (например, невалидный UUID) → `400 Bad Request`.
- **Query-параметры** — передаются в строке запроса (`?withProfile=true`). Как правило
  необязательны и имеют значение по умолчанию (обычно нулевое значение типа, например
  `false` для `bool`). Параметры-списки передаются повторением ключа:
  `?muscle_group=chest&muscle_group=triceps`.
- **Тело запроса (body)** — JSON в теле запроса для `POST`- и `PATCH`-эндпоинтов,
  `Content-Type: application/json`. Обязательные поля отмечены в Swagger как `required`;
  их отсутствие или несоответствие формату (например, невалидный email) → `400`.

### `omitempty` в полях ответа

В JSON-ответах часть полей помечена как `omitempty` (это видно в Swagger по отсутствию
поля в `required`, и по факту — поле может отсутствовать в ответе). Если значение поля
пустое/нулевое, оно **не включается** в JSON вовсе, а не передаётся как `null` или `0`.

Например, в `UserProfile` поля `age`, `gender`, `height`, `weight` заполняются только
если пользователь их указал — если поле не заполнено, в ответе его не будет. Клиент
должен проверять наличие поля, а не полагаться на то, что оно всегда присутствует.

Аналогично сам объект `profile` в ответе `GET /users/{id}` присутствует только если
запрошен с `withProfile=true` и профиль существует.

### Коды ошибок

Все ошибки возвращаются в едином формате:

```json
{
  "key": "incorrect_password",
  "message": "incorrect password: error bad request"
}
```

`key` — машиночитаемый код ошибки (используется для локализации/обработки на клиенте),
`message` — человекочитаемое описание. Основные коды:

- **400 Bad Request** — невалидные входные данные: ошибка парсинга/валидации тела,
  path- или query-параметра, либо бизнес-валидация (например, email уже занят).
  `message` содержит детали ошибки.
- **401 Unauthorized** — отсутствует, невалиден или истёк `access_token`/`refresh_token`
  (ключи `invalid_token`, `token_expired`).
- **403 Forbidden** — сущность существует, но принадлежит другому пользователю
  (например, попытка изменить или удалить чужое упражнение).
- **404 Not Found** — запрашиваемая сущность не найдена (например, пользователь с
  указанным `id` или `email`).
- **500 Internal Server Error** — внутренняя ошибка сервера. В этом случае `key` всегда
  равен `undefined_error`, а `message` — общий текст `"internal server error"` без
  деталей (детали логируются на сервере, но не отдаются клиенту).

## Auth (`/auth/*`)

Эндпоинты регистрации и авторизации. Авторизация не требуется (публичные эндпоинты).

### `POST /auth/check-email`

Проверяет, свободен ли email для регистрации. Тело запроса — `email`. Ошибок с
собственным `key` нет — только общая валидация (`400`, если email не строка/не email).

### `POST /auth/signup`

Регистрация нового пользователя. При успехе возвращает пользователя и пару токенов
(см. [Токены и их использование](#токены-и-их-использование)).

Специфичные ошибки:

- `email_already_used` (`400`) — пользователь с таким email уже зарегистрирован.
- Общая валидация полей (`400`, `key: undefined_error`) — пароль короче 8 или длиннее
  64 символов, содержит недопустимые символы, `name`/`email`/`password` пустые, `name`
  длиннее 100 символов или `email` длиннее 256 символов.

### `POST /auth/login`

Вход по email и паролю. При успехе возвращает пользователя и пару токенов.

Специфичные ошибки:

- `incorrect_password` (`400`) — пароль не совпадает.
- `404` (`key: undefined_error`) — пользователь с таким email не найден.

### `POST /auth/refresh`

Обновление пары токенов по `refresh_token`. Возвращает новую пару `access_token` +
`refresh_token`; переданный `refresh_token` при этом инвалидируется (одноразовый).

Специфичные ошибки:

- `invalid_token` (`401`) — токен не прошёл проверку подписи/формата, либо уже был
  использован ранее (повторное использование `refresh_token`).
- `token_expired` (`401`) — `refresh_token` истёк (старше 10 дней).

### Восстановление пароля

Сброс пароля состоит из трёх последовательных шагов. Каждый шаг зависит от результата
предыдущего — использовать эндпоинты нужно строго по порядку.

1. **`POST /auth/password-recovery`** — запрос восстановления по email.
   Тело: `email`. Сервис находит пользователя, генерирует 6-значный числовой код,
   сохраняет его хэш (все предыдущие неиспользованные коды пользователя при этом
   становятся недействительными) и отправляет код на email асинхронно, письмом. Код
   живёт **10 минут**. Ответ — `200` без тела.

   Специфичные ошибки:
    - `404` (`key: undefined_error`) — пользователь с таким email не найден.

2. **`POST /auth/password-recovery/verify`** — проверка кода из письма.
   Тело: `email`, `code` (строго 6 цифр). При совпадении кода сервис помечает его
   использованным и выдаёт одноразовый `reset_token` — непрозрачную строку, которую
   нужно передать на следующем шаге. `reset_token` живёт **15 минут**.

   Специфичные ошибки:
    - `recovery_code_invalid` (`400`) — для пользователя нет неиспользованного кода
      (не запрашивался или уже использован), либо код найден, но введённое значение не
      совпадает.
    - `recovery_code_expired` (`400`) — код найден и не использован, но истёк по времени
      (старше 10 минут).

3. **`POST /auth/password-recovery/reset`** — установка нового пароля.
   Тело: `new_password`, `reset_token` (полученный на шаге 2). При успехе пароль
   меняется, `reset_token` инвалидируется, и в ответе сразу выдаётся пара
   `access_token`/`refresh_token` — повторный логин не требуется (см.
   [Токены и их использование](#токены-и-их-использование)).

   Специфичные ошибки:
    - `reset_token_invalid` (`400`) — токен не найден, уже использован, либо пользователь,
      к которому он привязан, не существует.
    - `reset_token_expired` (`400`) — токен найден, но истёк (старше 15 минут).

## Users (`/users/*`)

Требует авторизации — заголовок `Authorization: Bearer <access_token>` (см.
[JWT авторизация](#jwt-авторизация)). При отсутствии/невалидности/истечении токена
возвращается `401` с ключом `invalid_token` или `token_expired`.

### `GET /users/{id}`

Получение пользователя по `id`.

Параметры:

- `id` (path, обязателен) — UUID пользователя. Невалидный UUID → `400`.
- `withProfile` (query, необязателен, по умолчанию `false`) — если `true`, в ответе
  дополнительно будет объект `profile` с антропометрическими данными пользователя (см.
  [`omitempty` в полях ответа](#omitempty-в-полях-ответа) — сам `profile` и его поля
  включаются в ответ только если заполнены).

Специфичные ошибки:

- `404` (`key: undefined_error`) — пользователь с указанным `id` не найден.

### `GET /users/me`

То же самое, что `GET /users/{id}`, но без указания `id` в пути — пользователь
определяется по `userID` из переданного `access_token`. Удобно, когда клиенту не нужно
отдельно хранить свой `id`.

Параметры:

- `withProfile` (query, необязателен, по умолчанию `false`) — как в `GET /users/{id}`.

Специфичные ошибки: те же, что у `GET /users/{id}`.

### `PATCH /users/me/profile`

Частичное обновление профиля текущего пользователя (определяется по `access_token`, как
в `GET /users/me`). Все поля тела запроса необязательны и обновляют только те
параметры, которые переданы, — остальные значения профиля остаются как были.

Тело запроса:

- `age` (необязателен) — 1–150.
- `gender` (необязателен) — `male` или `female`.
- `height` (необязателен) — рост в см, 1–300.
- `weight` (необязателен) — вес в кг, 1–500.

В ответе возвращается объект профиля целиком (`age`/`gender`/`height`/`weight`) после
обновления, с той же семантикой `omitempty`, что и в `GET /users/{id}` (см.
[`omitempty` в полях ответа](#omitempty-в-полях-ответа)).

Специфичные ошибки:

- `404` (`key: undefined_error`) — профиль текущего пользователя не найден.

## Exercises (`/exercises/*`, `/muscle-groups`, `/equipments`)

Упражнения бывают трёх видов:

- **базовые** — общий каталог, у них нет владельца (`owner_id` в ответе отсутствует);
- **свои** — кастомные упражнения пользователя, по умолчанию видны только ему;
- **публичные** — кастомные упражнения, у которых автор выставил `is_public = true`.

### `GET /muscle-groups`, `GET /equipments`

Справочники допустимых значений для полей `muscle_groups` и `equipment`. Авторизация не
нужна. Каждый возвращает массив объектов с полями `key` (уникальный ключ) и `name`
(название для отображения):

```json
[
  { "key": "chest", "name": "Грудные" },
  { "key": "abs", "name": "Пресс" }
]
```

В фильтрах списка и в телах запросов используются ключи (`key`), а не названия.

### `GET /exercises`

Список упражнений с фильтрацией и пагинацией. **Опциональная авторизация**: без токена
доступны только базовые и публичные упражнения, с токеном — ещё и свои.

Параметры (query):

- `type` (обязателен) — какой набор вернуть:
    - `basic` — только базовые;
    - `public` — публичные упражнения других пользователей;
    - `own` — только свои (**нужен токен**);
    - `all` — базовые + публичные + свои (без токена — только базовые и публичные).
- `muscle_group` (необязателен, можно несколько) — вернуть упражнения, у которых есть
  **хотя бы одна** из указанных групп мышц.
- `equipment` (необязателен, можно несколько) — вернуть упражнения, которые можно
  выполнить с указанным инвентарём, то есть весь требуемый инвентарь упражнения входит в
  переданный набор.
- `search` (необязателен) — поиск по названию (подстрока, без учёта регистра).
- `limit` (необязателен, по умолчанию 20) — размер страницы, от 1 до 1000.
- `offset` (необязателен, по умолчанию 0) — смещение, от 0 до 100000.

Результат отсортирован по названию. Дубликаты в `muscle_group` и `equipment`
игнорируются.

Специфичные ошибки:

- `400` — отсутствует или невалидный `type`, `limit` или `offset` вне допустимого
  диапазона, значение `muscle_group` или `equipment` не из справочника.
- `user_id_required_for_filter` (`400`) — запрошен набор, для которого нужна
  авторизация, а токен не передан.
- `invalid_token` / `token_expired` (`401`) — токен передан, но невалиден или истёк.

### `GET /exercises/{id}`

Получение упражнения по `id`. Требует авторизации. Доступны базовые, свои и публичные
упражнения других авторов.

Специфичные ошибки:

- `400` — невалидный UUID.
- `404` — упражнение не найдено.
- `403` — приватное упражнение другого пользователя.

### `POST /exercises`

Создание кастомного упражнения. Требует авторизации, владельцем становится
пользователь из токена.

Тело запроса:

- `name` (обязателен) — непустая строка, не длиннее 255 символов.
- `is_public` (необязателен, по умолчанию `false`).
- `description` (необязателен).
- `muscle_groups`, `equipment` (необязательны, по умолчанию пустые) — значения из
  справочников `GET /muscle-groups` и `GET /equipments`.

В ответе возвращается созданное упражнение.

Специфичные ошибки:

- `400` — пустое или слишком длинное `name`, значение `muscle_groups` или `equipment` не
  из справочника.

### `PATCH /exercises/{id}`

Частичное обновление своего упражнения. Требует авторизации. Все поля тела
необязательны, кроме `id`: он обязан совпадать с `id` в пути. Можно менять `name`,
`description`, `is_public`, `muscle_groups`, `equipment`. Для `name`, `muscle_groups` и
`equipment` действуют те же ограничения, что и в `POST /exercises`. В ответе возвращается
обновлённое упражнение.

Поле, которого нет в теле запроса, не меняется. Пустой массив в `muscle_groups` или
`equipment` очищает только этот массив.

Специфичные ошибки:

- `400` — невалидный UUID, `id` в теле не совпадает с `id` в пути, пустое или слишком
  длинное `name`, значение `muscle_groups` или `equipment` не из справочника.
- `403` — упражнение не ваше (в том числе любое базовое).
- `404` — упражнение не найдено.

### `DELETE /exercises/{id}`

Удаление своего упражнения. Требует авторизации. Удаление «мягкое»: упражнение исчезает
из списков, но остаётся в БД, чтобы не ломать будущие ссылки из тренировок. Ответ —
`200` без тела.

Специфичные ошибки:

- `400` — невалидный UUID.
- `403` — упражнение не ваше (в том числе любое базовое).
- `404` — упражнение не найдено или уже удалено.

### Поля упражнения в ответе

`id`, `name`, `description` (`omitempty`), `owner_id` (`omitempty`, у базовых
упражнений отсутствует), `is_public`, `muscle_groups`, `equipment`, `created_at`.

## Programs (`/default-programs/*`, `/programs/*`)

Устройство программ описано в [programs.md](programs.md). Дни недели везде передаются
числами ISO: 1 — понедельник, 7 — воскресенье.

Каталог готовых программ (`/default-programs`) доступен без авторизации. Программы
пользователя (`/programs`) требуют авторизации и доступны только владельцу: чужая
программа → `403`, несуществующая → `404`.

### `GET /default-programs`

Каталог готовых программ, без дней, отсортирован по названию. Параметры (query,
необязательны):

- `day_of_week` (можно несколько) — выбранные дни недели; возвращаются программы, у
  которых число тренировок в неделю равно числу переданных дней;
- `goal` — `strength`, `muscle`, `fitness`, `fat_loss`, `endurance`;
- `level` — `beginner`, `intermediate`, `advanced`.

Специфичные ошибки:

- `400` — день недели вне 1–7 или повторяющийся, неизвестные `goal` или `level`.

### `GET /default-programs/{id}`

Готовая программа с `days_per_week`, `weeks_count` и тренировками. У каждой тренировки
есть `week_number`, `order_index` (позиция в неделе) и шаблон: `id`, `name`, `focus`,
`equipment` и упражнения (`exercise_id`, `exercise_name`, `order_index`, `sets`,
`target_reps`, `target_percent_1rm`, `rest_seconds`). Процент от рекорда задан не у всех упражнений.

Специфичные ошибки:

- `400` — невалидный UUID.
- `404` — программа не найдена.

### `GET /programs`

Программы текущего пользователя без недель и упражнений, от недавно изменённых к давним.
Пагинации нет. Параметр `state` (query, необязателен) — `draft`, `needs_measurement`,
`in_progress` или `finished`.

Специфичные ошибки:

- `400` — неизвестное значение `state`.

### `GET /programs/{id}`

Программа целиком. В `weeks` перечислены все недели от 1 до `weeks_count`, в каждой
неделе — все дни из `days_of_week`; у дня без упражнений `exercises` пустой массив.

```json
{
  "id": "…",
  "name": "Верх / низ",
  "source_kind": "default",
  "default_program_id": "…",
  "goal": "muscle",
  "level": "intermediate",
  "state": "in_progress",
  "days_of_week": [1, 4],
  "weeks_count": 2,
  "start_date": "2026-11-16",
  "weeks": [
    {
      "week_number": 1,
      "days": [
        {
          "day_of_week": 1,
          "exercises": [
            {
              "id": "…",
              "exercise_id": "…",
              "exercise_name": "Жим штанги лёжа",
              "order_index": 0,
              "sets": 4,
              "target_reps": 8,
              "target_weight_kg": 60,
              "rest_seconds": 120
            }
          ]
        },
        { "day_of_week": 4, "exercises": [] }
      ]
    }
  ],
  "required_measurements": [],
  "created_at": "2026-11-13T10:00:00Z",
  "updated_at": "2026-11-13T10:00:00Z"
}
```

`source_kind` — `default` (из каталога) или `custom` (создана с нуля).
У упражнения нагрузка задаётся либо весом `target_weight_kg`, либо процентом от личного
рекорда `target_percent_1rm` (больше 0 и не больше 100), либо не задаётся. Вес по проценту
сервер не считает: клиент берёт последний рекорд пользователя в этом упражнении
(`GET /users/{id}/prs`).

`required_measurements` — упражнения программы с процентной нагрузкой, по которым у
пользователя ещё нет ни одного рекорда (`exercise_id`, `exercise_name`). Список заполнен
только у программ, которые ещё не начаты. Пока он не пуст, программа в состоянии
`needs_measurement`. Рекорды добавляются через `POST /users/{id}/prs`, и когда нужные
есть, программа сама возвращается в `draft`.

`default_program_id`, `start_date`, `target_weight_kg`, `target_percent_1rm` и
`rest_seconds` могут отсутствовать (см. [`omitempty` в полях ответа](#omitempty-в-полях-ответа)).
Остальные запросы, возвращающие программу целиком, отвечают в этом же формате.

### `POST /programs`

Создаёт черновик из метаданных, программа сразу появляется в списке. Тело запроса:

- `name` (обязателен) — непустая строка, не длиннее 255 символов;
- `goal`, `level` (обязательны) — значения из `GET /default-programs`;
- `days_of_week` (необязателен) — дни недели, общие для всех недель;
- `weeks_count` (необязателен, по умолчанию 1) — от 1 до 52.

Структура заполняется отдельно: `PUT /programs/{id}/structure` или
`PUT /programs/{id}/weeks/{week}`.

Специфичные ошибки:

- `400` — пустое или слишком длинное `name`, неизвестные `goal` или `level`, неверные
  `days_of_week`, `weeks_count` вне 1–52.

### `POST /programs/from-default`

Создаёт черновик копированием готовой программы. Тело запроса: `default_program_id` и
`days_of_week` — выбранные дни, без повторов, их число должно равняться `days_per_week`
программы. Название, цель и уровень берутся из готовой программы, число недель тоже.
Тренировки каждой недели раскладываются на выбранные дни по порядку: первая — на самый
ранний день.

Если у пользователя нет рекордов по упражнениям с процентной нагрузкой, программа
создаётся в состоянии `needs_measurement` и список таких упражнений приходит в
`required_measurements`.

Специфичные ошибки:

- `days_count_mismatch` (`400`) — число выбранных дней не равно `days_per_week`.
- `400` — неверные `days_of_week`.
- `404` — готовая программа не найдена.

### `PATCH /programs/{id}`

Частичное обновление метаданных: `name`, `goal`, `level`, `days_of_week`, `weeks_count`.
Поле, которого нет в теле, не меняется. Пустой `days_of_week` убирает все дни. Дни и
недели общие для всей программы: упражнения убранных дней и недель удаляются, а новые дни
и недели остаются пустыми. Ограничения те же, что в `POST /programs`.

Специфичные ошибки:

- `program_read_only` (`400`) — программа завершена.
- `400` — невалидные значения полей.

### `PUT /programs/{id}/structure`

Полная замена дней недели, недель и упражнений. Тело запроса:

```json
{
  "days_of_week": [1, 4],
  "weeks": [
    {
      "days": [
        {
          "day_of_week": 1,
          "exercises": [
            { "exercise_id": "…", "sets": 4, "target_reps": 8, "target_weight_kg": 60, "rest_seconds": 120 }
          ]
        }
      ]
    }
  ]
}
```

Номер недели — позиция в `weeks`, `weeks_count` становится равным их числу (пустой массив
даёт одну пустую неделю). `day_of_week` в неделе должен входить в `days_of_week` и не
повторяться. Порядок упражнений в дне — порядок в массиве. `sets` — от 1 до 20,
`target_reps` — не меньше 1, `target_weight_kg`, `target_percent_1rm` (нельзя вместе с
весом) и `rest_seconds` необязательны. После сохранения состояние не начатой программы
пересчитывается: если появилась процентная нагрузка без рекорда, она становится
`needs_measurement`, и наоборот. Тем же
запросом структуру заполняют впервые и меняют позже.

Специфичные ошибки:

- `program_read_only` (`400`) — программа завершена.
- `exercise_not_available` (`400`) — упражнение не найдено, удалено или чужое непубличное.
  Упражнения, которые уже есть в программе, не проверяются.
- `400` — невалидные дни, число недель больше 52, невалидные подходы, повторы или вес.

### `PUT /programs/{id}/weeks/{week}`

Замена упражнений одной недели. Тело запроса — `days`, как в одной неделе
`PUT /programs/{id}/structure`; дни недели должны входить в `days_of_week` программы,
остальные недели не меняются. Дни, не указанные в теле, остаются в неделе пустыми.

Специфичные ошибки:

- `program_read_only`, `exercise_not_available` (`400`) — как в `PUT /programs/{id}/structure`.
- `400` — `week` не число или вне 1–`weeks_count`, дни и упражнения невалидны.

### `POST /programs/{id}/start`

Переводит черновик в `in_progress` и фиксирует `start_date`. Если у пользователя уже была
программа в процессе, она той же транзакцией становится `finished`, а её `id` приходит в
поле `finished_program_id` (иначе поля нет). Ответ — программа целиком.

Специфичные ошибки:

- `measurement_required` (`400`) — нет рекордов по упражнениям с процентной нагрузкой,
  они перечислены в `required_measurements`.
- `program_incomplete` (`400`) — нет дней недели или в каком-то дне какой-то недели нет
  упражнений.
- `invalid_state_transition` (`400`) — программа не черновик и не ждёт замера.

### `POST /programs/{id}/finish`

Переводит программу из `in_progress` в `finished`. Ответ — программа целиком.

Специфичные ошибки:

- `invalid_state_transition` (`400`) — программа не в процессе.

### `DELETE /programs/{id}`

Удаление программы, которая ещё не начата (`draft` или `needs_measurement`), вместе со
всем содержимым. Ответ — `200` без тела.

Специфичные ошибки:

- `program_not_draft` (`400`) — программа уже начата или завершена.

## Personal records (`/users/{id}/prs`)

Личные рекорды (PR) пользователя в упражнениях. Требует авторизации. Рекорды доступны
только их владельцу: чужой `id` → `403`, при этом не проверяется, существует ли такой
пользователь.

Рекорд — это вес в упражнении на момент записи. Записи только добавляются, текущим
считается последняя по времени, остальные образуют историю. Поле `is_calculated`
показывает, что значение оценено по формуле (по рабочему подходу), а не поднято на один
повтор.

### `POST /users/{id}/prs`

Добавляет рекорд. Тело запроса: `exercise_id`, `weight_kg` (больше 0 и меньше 10 000) и
необязательный `reps`. Без `reps` вес — это рекорд на один повтор. С `reps` вес — это вес
рабочего подхода, а рекорд оценивается по формуле Эпли (`вес × (1 + повторы / 30)`,
округление до сотых); при `reps` больше 1 `is_calculated` равен `true`, при `reps` равном
1 рекорд равен весу и `is_calculated` равен `false`. Ответ — созданный рекорд.

После добавления программы пользователя, которые ждали замера, пересчитываются: если
рекордов теперь хватает, они переходят в `draft`.

Специфичные ошибки:

- `exercise_not_available` (`400`) — упражнение не найдено, удалено или чужое
  непубличное.
- `400` — невалидный UUID, вес вне диапазона, `reps` меньше 1.
- `403` — запрос не от владельца.

### `POST /users/{id}/prs/bulk`

Добавляет рекорды в нескольких упражнениях за один запрос, например по списку
`required_measurements` программы. Тело запроса — `records`, массив от 1 до 100 элементов,
каждый в том же формате, что и тело `POST /users/{id}/prs` (`exercise_id`, `weight_kg`,
необязательный `reps`). Упражнения в запросе не должны повторяться. Рекорды добавляются в
одной транзакции: либо все, либо ни одного. Ответ — массив созданных рекордов в порядке
запроса. Состояния программ, которые ждали замера, пересчитываются один раз после всех
записей.

Специфичные ошибки:

- `exercise_not_available` (`400`) — хотя бы одно упражнение не найдено, удалено или чужое
  непубличное.
- `400` — пустой массив или больше 100 элементов, повтор упражнения, невалидный UUID,
  вес вне диапазона, `reps` меньше 1.
- `403` — запрос не от владельца.

### `GET /users/{id}/prs`

Последний рекорд в каждом упражнении, где у пользователя есть записи. Порядок не
гарантирован. Если записей нет, возвращается пустой массив.

```json
[
  {
    "id": "…",
    "exercise_id": "…",
    "exercise_name": "Жим штанги лёжа",
    "weight_kg": 116.67,
    "is_calculated": true,
    "created_at": "2026-11-13T10:00:00Z"
  }
]
```

Специфичные ошибки:

- `400` — невалидный UUID.
- `403` — чужие рекорды.

### `GET /users/{id}/prs/{exerciseId}`

История рекордов пользователя в упражнении, от новых к давним, в том же формате.
Упражнение без записей и несуществующее упражнение дают пустой массив. Пагинации нет.

Специфичные ошибки:

- `400` — невалидный UUID пользователя или упражнения.
- `403` — чужие рекорды.
