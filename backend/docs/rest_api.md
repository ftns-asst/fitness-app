# Fitness Assistant API — документация

Документация по внешнему REST API сервиса. Полные схемы тел запросов и ответов смотрите
в Swagger — здесь описаны только общие соглашения и специфика запросов по тегам.

**Swagger UI:** http://94.228.166.134:8181/api/v1/swagger/index.html

**Base URL:** `/api/v1`

---

## Общие принципы

### JWT авторизация

API использует JWT (JSON Web Token) для авторизации. Токен состоит из трёх частей —
`header.payload.signature`, и в payload есть два типа полей:

- **Публичные (registered) поля** — стандартные поля, определённые спецификацией JWT.
  Сервис использует `exp` (`expiresAt`) — время истечения токена.
- **Приватные (custom) поля** — специфичные для этого API. Сейчас это `userID` —
  идентификатор пользователя, к которому привязан токен.

Приватные поля клиенту разбирать не нужно — они нужны только серверу. Клиент должен
воспринимать токен как непрозрачную строку и просто передавать его в запросах.

### Токены и их использование

При успешной регистрации (`/auth/signup`) или входе (`/auth/login`) сервис выдаёт пару
токенов:

| Токен | Время жизни | Назначение |
|---|---|---|
| `access_token` | 30 минут | Передаётся в защищённых запросах для авторизации |
| `refresh_token` | 10 дней | Используется только для получения новой пары токенов |

Для доступа к защищённым эндпоинтам (например, `GET /users/{id}`) `access_token`
передаётся в заголовке:

```
Authorization: Bearer <access_token>
```

Когда `access_token` истекает, новую пару токенов нужно получить через
`POST /auth/refresh`, передав текущий `refresh_token` в теле запроса. `refresh_token`
одноразовый: после использования он помечается использованным, и повторно применить его
нельзя — в ответ на такую попытку сервер вернёт ошибку `invalid_token`.

### Параметры запроса

API использует три способа передачи параметров:

- **Path-параметры** — часть пути, например `id` в `/users/{id}`. Обязательны всегда,
  ошибка парсинга (например, невалидный UUID) → `400 Bad Request`.
- **Query-параметры** — передаются в строке запроса (`?withProfile=true`). Как правило
  необязательны и имеют значение по умолчанию (обычно нулевое значение типа, например
  `false` для `bool`).
- **Тело запроса (body)** — JSON в теле запроса для `POST`-эндпоинтов,
  `Content-Type: application/json`. Обязательные поля отмечены в Swagger как `required`;
  их отсутствие или несоответствие формату (например, невалидный email) → `400 Bad
  Request`.

### `omitempty` в полях ответа

В JSON-ответах часть полей помечена как `omitempty` (это видно в Swagger по отсутствию
поля в `required`, и по факту — поле может отсутствовать в ответе). Если значение поля
пустое/нулевое, оно **не включается** в JSON вовсе, а не передаётся как `null` или `0`.

Например, в `UserProfile` поля `age`, `gender`, `height`, `weight` заполняются только
если пользователь их указал — если поле не заполнено, в ответе его не будет. Клиент
должен проверять наличие поля, а не полагаться на то, что оно всегда присутствует.

Аналогично сам объект `profile` в ответе `GET /users/{id}` присутствует только если
запрошен с `withProfile=true` и профиль существует.

### Коды ошибок

Все ошибки возвращаются в едином формате:

```json
{
  "key": "incorrect_password",
  "message": "incorrect password: error bad request"
}
```

`key` — машиночитаемый код ошибки (используется для локализации/обработки на клиенте),
`message` — человекочитаемое описание. Основные коды:

- **400 Bad Request** — невалидные входные данные: ошибка парсинга/валидации тела,
  path- или query-параметра, либо бизнес-валидация (например, email уже занят).
  `message` содержит детали ошибки.
- **401 Unauthorized** — отсутствует, невалиден или истёк `access_token`/`refresh_token`
  (ключи `invalid_token`, `token_expired`).
- **404 Not Found** — запрашиваемая сущность не найдена (например, пользователь с
  указанным `id` или `email`).
- **500 Internal Server Error** — внутренняя ошибка сервера. В этом случае `key` всегда
  равен `undefined_error`, а `message` — общий текст `"internal server error"` без
  деталей (детали логируются на сервере, но не отдаются клиенту).

## Auth (`/auth/*`)

Эндпоинты регистрации и авторизации. Авторизация не требуется (публичные эндпоинты).

### `POST /auth/check-email`

Проверяет, свободен ли email для регистрации. Тело запроса — `email`. Ошибок с
собственным `key` нет — только общая валидация (`400`, если email не строка/не email).

### `POST /auth/signup`

Регистрация нового пользователя. При успехе возвращает пользователя и пару токенов
(см. [Токены и их использование](#токены-и-их-использование)).

Специфичные ошибки:

- `email_already_used` (`400`) — пользователь с таким email уже зарегистрирован.
- Общая валидация полей (`400`, `key: undefined_error`) — пароль короче 8 или длиннее
  64 символов, содержит недопустимые символы, либо `name`/`email`/`password` пустые.

### `POST /auth/login`

Вход по email и паролю. При успехе возвращает пользователя и пару токенов.

Специфичные ошибки:

- `incorrect_password` (`400`) — пароль не совпадает.
- `404` (`key: undefined_error`) — пользователь с таким email не найден.

### `POST /auth/refresh`

Обновление пары токенов по `refresh_token`. Возвращает новую пару `access_token` +
`refresh_token`; переданный `refresh_token` при этом инвалидируется (одноразовый).

Специфичные ошибки:

- `invalid_token` (`401`) — токен не прошёл проверку подписи/формата, либо уже был
  использован ранее (повторное использование `refresh_token`).
- `token_expired` (`401`) — `refresh_token` истёк (старше 10 дней).

## Users (`/users/*`)

Требует авторизации — заголовок `Authorization: Bearer <access_token>` (см.
[JWT авторизация](#jwt-авторизация)). При отсутствии/невалидности/истечении токена
возвращается `401` с ключом `invalid_token` или `token_expired`.

### `GET /users/{id}`

Получение пользователя по `id`.

Параметры:

- `id` (path, обязателен) — UUID пользователя. Невалидный UUID → `400`.
- `withProfile` (query, необязателен, по умолчанию `false`) — если `true`, в ответе
  дополнительно будет объект `profile` с антропометрическими данными пользователя (см.
  [`omitempty` в полях ответа](#omitempty-в-полях-ответа) — сам `profile` и его поля
  включаются в ответ только если заполнены).

Специфичные ошибки:

- `404` (`key: undefined_error`) — пользователь с указанным `id` не найден.
