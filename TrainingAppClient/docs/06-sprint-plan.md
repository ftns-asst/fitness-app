# План спринтов: рекомендации, каталог, «Сегодня», КБЖУ и ввод значений

> План реализации требований из `05-recommendations-catalog-today.md`
> (issues 45–52). Спринты идут в порядке зависимостей; каждый заканчивается
> работающей вертикалью, а не «половиной слоя».
> Связанные документы: `04-roadmap.md` (issues, gates, статус),
> `02-program-model.md` (модель), `05-recommendations-catalog-today.md`
> (требования и решения), `CODE_STYLE.md` (стиль C++).
> Спринты S1–S8 соответствуют issues 47, 48, 45, 46, 49, 51, 50, 52
> предложения `05-recommendations-catalog-today.md` §5 и разделу §11.5.

## 1. Правила планирования

План наследует три правила из `04-roadmap.md`, и они же определяют границы
спринтов:

1. **Внутри среза сначала C++, потом UI.** Спринт, который начинается с QML и
   заканчивается заглушкой, считается невыполненным.
2. **Экран не считается готовым без аудита вёрстки** на 360/390/480, в
   framed-режиме и в тёмной теме (`--diag`, `problems=0`).
3. **Измеримый срез не считается готовым без теста.** Для каждого среза ниже
   указано, что именно проверяется тестом.

Три правила жёстко удорожают UI-спринты: один новый экран добавляет **5
автоматических тестов** в матрицу `ui_smoke` (`tests/CMakeLists.txt`),
поэтому в спринт берётся столько экранов, сколько успевает покрыть один
прогон CTest.

## 4. Спринты

### S1 — Каталог программ (issue 47)

**Цель:** созданная программа появляется в списке, который видит
пользователь.

| Часть | Содержание |
|---|---|
| C++ | `AProgram_Repository::Load_Programs(user_id)` — список всех программ со сводкой (название, цель, срок, прогресс, число тренировок); `Avm_Program_Catalog` + роли списка в `Program_Rows`; экспорт типа в QML |
| UI | `ProgramCatalogPage.qml`: группы по состоянию, карточка строки, кнопка «Создать программу»; вход из вкладок |
| Тесты | `tst_Program_Repository` (список пуст / одна программа / все состояния / сортировка по `updated_at`), `tst_Program_Catalog_VM` (роли, активная ровно одна) |

**Готово, когда:** программа, созданная в редакторе, видна в каталоге; список
пуст — не ошибка, а приглашение создать.

**Риск:** сводка в списке требует агрегатов по фактам. Если считать их в
`Load_Programs`, репозиторий станет тяжёлым — выносить в
`AsProgress_Calculator` (уже есть) и передавать готовые числа.

### S2 — Открытие, правка и статистика из каталога (issue 48)

**Цель:** из каталога доступны три действия.

| Часть | Содержание |
|---|---|
| C++ | параметризация `Avm_Program.reload(user_id, program_id)` и `Avm_Program_Stats` по `programId`; read-only для `completed`/`archived` (`Is_Read_Only_State`) |
| UI | переходы каталог → обзор → редактор → статистика; запрет редактирования структуры в read-only программе с понятным объяснением |
| Тесты | `tst_Program_VM` (чтение неактивной программы, read-only отказ), `tst_Program_Stats_VM` (статистика завершённой) |

### S3 — Питание: углеводы и жиры (issue 45)

**Цель:** КБЖУ выражается моделью.

| Часть | Содержание |
|---|---|
| C++ | `CarbsGrams`, `FatGrams` в `ERule_Metric`; обновление `CHECK` в `program_rules` и массивов текстов enum; типовые коды `carbs`, `fat`; `Average_Carbs/Fat` в `SProgram_Stats` и `Stats_Encoder` |
| UI | блок «Питание» в редакторе правил: углеводы и жиры рядом с белком |
| Тесты | `tst_Program_Model` (конверсия новых enum в строку и обратно — главный риск среза), `tst_Sql_Database` (миграция принимает новые значения и отвергает мусор) |

**Готово, когда:** правило по углеводам создаётся и переживает цикл
сохранения/чтения, а статистика показывает средние углеводы и жиры.

### S4 — Текстовые рекомендации (issue 46)

**Цель:** пользователь пишет рекомендации сам.

| Часть | Содержание |
|---|---|
| C++ | ослабление `CHECK` в `program_rules` миграцией v3; `Add_Advice` в сервисе; определение вида правила по наличию цели |
| UI | многострочное поле текста в конструкторе правила; текстовые рекомендации в списке без чекбокса |
| Тесты | `tst_Sql_Database` (текстовое правило без цели принимается, измеримое без цели — нет), `tst_Rule_Engine` (текстовое правило не меняет adherence) |

**Риск:** ослабление `CHECK` должно сохранить защиту от бессмысленных строк —
правило без цели, без текста и без заголовка не принимается.

### S5 — «Сегодня» на данных (issue 49)

**Цель:** главная перестаёт быть mock-экраном.

| Часть | Содержание |
|---|---|
| C++ | `Avm_Today`: активная программа, слот по сегодняшней дате, упражнения дня, правила с состоянием отметок; подстановка «Сегодня» из локальной даты устройства |
| UI | `TodayPage` на C++: дата и день недели, название программы, блок дня (тренировка / отдых / кардио / мобилити), рекомендации по категориям из §3.1 документа 05 |
| Тесты | `tst_Today_VM` (день отдыха, нет программы, программа есть, план не найден), smoke-тесты `today` × 5 компоновок |

**Готово, когда:** `TodayViewModel.qml` больше не читает `MockCatalog`, а все
четыре состояния из спецификации отличаются от предыдущего.

### S6 — Ввод значений на главной (issue 51)

**Цель:** текущие значения вводятся с главной и учитываются статистикой.

| Часть | Содержание |
|---|---|
| C++ | `Avm_Today.measurements`, `saveMeasurement`, `saveCheckins`; вызов инвалидации кэша `AStats_Repository` из точки записи |
| UI | секция «Замеры» (вес + сворачиваемые обхваты) и секция «Отметки» (сон, вода, шаги, белок) |
| Тесты | `tst_Today_VM` (повторный ввод за день обновляет запись, а не создаёт вторую; повторная отметка не увеличивает счётчик), `tst_Stats_Repository` (инвалидация по замеру и по отметке) |

### S7 — Авторасчёт КБЖУ (issue 50)

**Цель:** кнопка «Рассчитать» даёт предложение по КБЖУ.

| Часть | Содержание |
|---|---|
| C++ | `birth_date` и `activity_level` в профиле миграцией; `AsMacro_Calculator` (BMR → TDEE → макросы) с именованными коэффициентами активности; `SMacro_Suggestion` с основанием расчёта |
| UI | кнопка «Рассчитать» рядом с метриками питания; предпросмотр **до** применения; выбор режима (поддержание / дефицит 15 % / плюс 10 %) |
| Тесты | `tst_Macro_Calculator` (каждый коэффициент активности закреплён своим тестом; результат не пишется в цели без действия пользователя; без возраста и активности расчёт не запускается) |

**Риск:** без `birth_date` и `activity_level` расчёт невозможен — это миграция
профиля, и её надо делать в этом же спринте, иначе кнопка будет
неработающей.

### S8 — Ползунок веса и блок «Объёмы» (issue 52 + issue 11)

**Цель:** ввод подхода удобен, тоннаж и рабочий вес видны.

| Часть | Содержание |
|---|---|
| C++ | изменений не требует: рабочий вес, e1RM и тоннаж уже считаются из подходов |
| UI | `WeightRuler.qml` (шаг 2,5 кг, метки каждые 10 кг, тактильный отклик), `RepsWheel.qml`; блок «Объёмы» на главной и в профиле (тоннаж недели, тоннаж программы, рабочий вес, дельты обхватов) |
| Тесты | smoke-тесты экрана записи подхода × 5 компоновок; проверка, что ползунок выдаёт только значения, кратные шагу инвентаря |

**Зависимость:** пересекается с issue 11 из фазы S2 (`04-roadmap.md`) —
сделать один раз вместе, иначе два разных контрола ввода веса.

## 5. Риски

| Риск | Спринт | Что делаем |
|---|---|---|
| Сводка в списке программ утяжелит репозиторий | S1 | агрегаты считает `AsProgress_Calculator`, репозиторий отдаёт готовые числа |
| Ослабление `CHECK` открыт��ет мусорные правила | S4 | правило без цели, текста и заголовка не принимается — тест на отказ |
| Новые enum ломают конверсию строка ↔ значение | S3 | тест на полный цикл конверсии для `carbs` и `fat` — первый тест спринта |
| `birth_date`/`activity_level` не добавлены | S7 | миграция в том же спринте; без неё кнопка нерабочая |
| Два разных контрола ввода веса | S8 | один компонент вместе с issue 11 |
| Растёт число тестов → CTest медленнее | все | тесты домена быстрые, основное время — smoke; запускать по `-j 4` |

## 6. Контроль качества на каждом спринте

Обязательный набор (совпадает с gates `04-roadmap.md` §2):

1. `ctest` зелёный, число тестов выросло.
2. `clang-format --dry-run --Werror`, `scan_style.ps1` — 0 нарушений.
3. `qmlformat` и `qmllint` чистые.
4. `--diag`: `problems=0` на 360/390/480, frame и dark для каждого нового
   экрана.
5. Скриншот нового экрана в `docs/ui-preview/`.
6. `git diff --check` без предупреждений.

Новый экран добавляется в матрицу `tests/CMakeLists.txt` — это 5 тестов,
они обязаны быть в том же спринте, что и экран.

## 7. С чего начинать

Рекомендуемая точка старта — **S1 (каталог)**. Причина не в порядке
удобства, а в том, что остальные спринты об одном и том же:

- S2, S5, S6 не имеют смысла без списка программ — пользователь создаёт
  программу и не может её найти;
- S3 и S4 меняют ту же сущность правил, что уже проверена в S1–S2, поэтому
  делать их на проверенном фундаменте дешевле;
- S7 и S8 независимы и могут идти параллельно, если нужен ранний
  результат на главной.

Альтернативный старт — **S3 (макросы)**: он самый маленький (1,5–2 дня),
не требует миграции чужой схемы и даёт быстрый результат, который можно
показать. Но он ничего не меняет в пользовательском пути, пока не закрыты
S1–S2.
