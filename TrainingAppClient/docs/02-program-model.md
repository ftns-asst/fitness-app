# Модель программы тренировок, правил и статистики

> Статус: **проект** (документ ничего не меняет в коде; фиксирует целевую модель).
> Реализация — фазы A/B дорожной карты: схема v2 (issue 22), расчёты и правила
> (issue 25), «взять план» (issue 28), показ статистики (issue 31), серверный
> контракт plans/workouts/stats (issue 35).
> Связанные документы: `fitness-assistant-frontend-design.md` (экраны),
> `mock-data-contract.md` (роли моделей и DTO), `04-roadmap.md` (фазы),
> `03-api-contract.md` (серверные данные и открытые вопросы).

## 1. Термины

| Термин | Имя в коде / схеме | Определение |
|---|---|---|
| **Глобальная программа** | `SProgram`, таблица `programs` | Личный экземпляр программы пользователя: цель, срок, недельный план, правила, факты, статистика. В UI — «Моя программа». |
| **Шаблон (каталожный план)** | `plans`, `plan_days`, `day_exercises` | Готовый план каталога: автор, рейтинг, отзывы, дни. Пользователь его не редактирует; источник для «Взять план» и «Скопировать и изменить». |
| **Цель** | `Goal` + `SGoal_Target` | Enum-цель (`strength`, `muscle`, `fitness`, `fatLoss`, `endurance`) и измеримые целевые значения (вес, рабочий вес, частота, обхваты). |
| **Срок** | `STerm` | `startDate` + `weeksTotal` (производный `endDate`) либо открытый срок «до достижения цели». |
| **Недельный план** | `SWeek_Slot`, таблица `program_schedule` | Семь слотов (Пн…Вс) либо циклическая ротация: слот ссылается на день плана или на отдых. |
| **День плана** | `SProgram_Day`, таблица `program_days` | Индивидуально настраиваемый состав упражнений одного дня (`workout`, `rest`, `cardio`, `mobility`, `optional`). |
| **Предписание упражнения** | `SDay_Exercise`, таблица `program_day_exercises` | Строка дня: упражнение, подходы, диапазон повторов, целевой вес, RPE, отдых, темп, суперсет, правило прогрессии. |
| **Правило** | `SProgram_Rule`, таблица `program_rules` | Директива программы: питание, восстановление, образ жизни, техника. Пример — белок 1,8 г/кг/день. |
| **Отметка правила** | `SRule_Checkin`, таблица `rule_checkins` | Факт по правилу за день/неделю: значение, состояние `done/failed/skipped/unknown`, источник (ручной, расчётный или из дневника питания). |
| **Дневник питания** (резерв, post-MVP) | `SNutrition_Entry`, таблица `nutrition_entries` | Опциональный источник значения для правил питания: продукт/позиция, порция, БЖУ и калории (§3.10). |
| **Сессия (факт)** | `SWorkout_Session`, таблица `workouts` | Выполненная тренировка (или черновик) с датой, длительностью, тоннажом, отклонениями от плана. |
| **Подход (факт)** | `SSet_Log`, таблица `sets` | Фактический подход: вес, повторы, RPE, разминочный флаг. |
| **Статистика программы** | `SProgram_Stats` | Производные метрики одной программы за её срок (объём, выполнение, прогресс, правила). |
| **Общая статистика** | `SLifetime_Stats` | Агрегат по всем программам пользователя: лайфтайм-итоги, рекорды, сравнение программ. |

Соглашения: день недели — ISO 8601 (`1` = понедельник … `7` = воскресенье);
дата — `YYYY-MM-DD`; время — ISO 8601 UTC; вес — кг (число, шаг 0,5); RPE —
число 5–10 с шагом 0,5, где `0` означает «не введён»; enum-значения —
стабильные ASCII-строки, перевод выполняет UI (`mock-data-contract.md` §1).

Имена структур — предварительные (`AS`-стиль, `CODE_STYLE.md`): `SProgram`,
`SGoal_Target`, `STerm`, `SWeek_Slot`, `SProgram_Day`, `SDay_Exercise`,
`SProgram_Rule`, `SRule_Checkin`, `SWorkout_Session`, `SSet_Log`,
`SProgram_Stats`, `SLifetime_Stats`; репозиторий — `AProgram_Repository`,
сервисы — `AsRule_Engine`, `AsProgress_Calculator` (расширение issue 25).

## 2. Иерархия и происхождение данных

```text
plans (каталог, read-only)          programs (экземпляр пользователя)
├─ plan_days                         ├─ goal + goal_targets[]
│  └─ day_exercises ─ exercises      ├─ term (startDate, weeksTotal, endDate)
└─ reviews, rating                   ├─ program_schedule (7 слотов)
                                     │   └─ slot → program_day | rest
                                     ├─ program_days                 ← снимок шаблона
                                     │   └─ program_day_exercises ─ exercises
                                     ├─ program_rules[]              ← каталог правил + свои
                                     │   └─ rule_checkins[] (день/неделя)
                                     ├─ workouts[] (факты) ── sets[]
                                     └─ stats (производное)  →
Lifetime_Stats ← агрегат по всем programs (workouts/sets, checkins, замеры тела)
```

Ключевое решение: **взятие шаблона — снимок**. `program_days` и
`program_day_exercises` создаются копией строк шаблона; дальнейшие правки
шаблона в каталоге программу не меняют, а правки программы не влияют на
рейтинг и отзывы шаблона. Связь с шаблоном сохраняется как
`sourceTemplateId` (+ `sourceKind`) — ради «Похожие планы» и честной
аналитики, но не как владение.

## 3. Сущности

### 3.1. Программа (`SProgram` / `programs`)

| Поле | Тип | Обязательность | Назначение |
|---|---|---|---|
| `id` | string | да | идентификатор программы, стабильный |
| `userId` | string | да | владелец (граница auth, `docs/03` §4) |
| `title` | string | да | «Сила 12 недель», копируется из шаблона или вводится |
| `sourceKind` | enum | да | `template` (взята из каталога), `copy` (скопирована и изменена), `scratch` (создана с нуля), `matched` (результат подбора) |
| `sourceTemplateId` | string \| null | при `template` / `copy` / `matched` | исходный `plans.id` |
| `goal` | enum | да | `strength`, `muscle`, `fitness`, `fatLoss`, `endurance` |
| `goalTargets` | `SGoal_Target[]` | нет | измеримые целевые значения (3.2) |
| `term` | `STerm` | да | срок программы (3.3) |
| `level` | enum | да | `beginner`, `intermediate`, `advanced` (расширение enum профиля) |
| `scheduleKind` | enum | да | `weekday` (слоты по дням недели) или `rotation` (цикл по порядку) |
| `daysPerWeek` | int 1–7 | да | производное от расписания: число слотов `workout` |
| `state` | enum | да | `draft`, `active`, `paused`, `completed`, `cancelled`, `archived` |
| `revision` | int ≥1 | да | версия структуры программы, растёт при правке цели/срока/расписания/дней |
| `createdAt`, `updatedAt` | ISO 8601 | да | служебные метки |
| `actualStartDate`, `actualEndDate` | date \| null | нет | фактические границы (могут отличаться от плана) |
| `syncState` | enum | да | `synced`, `local`, `syncing`, `offline` (как `profile.syncState`) |
| `note` | string | нет | свободный комментарий пользователя |

Переходы состояний: `draft → active` (кнопка «Начать программу»),
`active → paused → active`, `active → completed` (срок истёк или цель
достигнута), `active → cancelled` (отказ), `completed|cancelled → archived`
(автоматически через N дней). В `archived` структура read-only, статистика
сохраняется и входит в общую.

### 3.2. Цель и целевые значения (`SGoal_Target`)

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор |
| `metric` | enum | `bodyWeightKg`, `workingWeightKg`, `bodyFatPercent`, `measurementCm`, `workoutsPerWeek`, `tonnagePerWeekKg`, `repsAtWeight` |
| `exerciseId` | string \| null | заполняется для метрик, привязанных к упражнению (`workingWeightKg`, `repsAtWeight`) |
| `measurementKey` | enum \| null | для `measurementCm`: `chest`, `waist`, `hip`, `arm`, `thigh` |
| `unit` | enum | `kg`, `percent`, `cm`, `count`, `timesPerWeek` |
| `startValue` | number \| null | значение на старте (для дельты и прогресса) |
| `targetValue` | number | цель |
| `targetDate` | date \| null | срок достижения (может быть раньше конца программы) |
| `direction` | enum | `increase`, `decrease`, `maintain` — для правильной трактовки «лучше» |
| `state` | enum | `active`, `achieved`, `dropped` |

Цель-«упражнение» (`repsAtWeight`) хранит `targetWeightKg` и `targetReps`
отдельно; UI показывает «жим 100 кг на 5 повторов». Прогресс цели считается
в `AsProgress_Calculator` и доступен и в статистике программы, и в лайфтайме.

### 3.3. Срок (`STerm`)

| Поле | Тип | Назначение |
|---|---|---|
| `startDate` | date | плановая дата старта (обычно дата активации) |
| `weeksTotal` | int 1–52 \| 0 | 0 = открытый срок «до достижения цели» |
| `endDate` | date \| null | производное: `startDate + weeksTotal × 7 − 1 день` |
| `mode` | enum | `fixedWeeks`, `openEnded` |
| `extendedWeeks` | int ≥0 | суммарное продление (без перезаписи `weeksTotal`) |

Правила: `endDate` всегда производное — не хранить как независимое поле,
иначе возможно противоречие. Продление/сокращение срока — правка `weeksTotal`
+ `extendedWeeks`, инкремент `revision`, событие в журнале изменений (3.9) —
чтобы статистика знала, по какому плану считалось «план/факт».

### 3.4. Недельный план и индивидуальный план дня

**Слот недели (`SWeek_Slot` / `program_schedule`).** 7 строк для
`scheduleKind = weekday` либо N строк цикла для `rotation`.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор слота |
| `programId` | string | программа |
| `dayOfWeek` | int 1–7 \| null | ISO-день; `null` для `rotation` |
| `rotationIndex` | int ≥1 \| null | позиция в цикле; `null` для `weekday` |
| `programDayId` | string \| null | день плана; `null` = день отдыха |
| `kind` | enum | `workout`, `rest`, `optional`, `cardio`, `mobility` |
| `isAnchor` | bool | «якорный» день: переносить нельзя (для плавающего графика) |
| `note` | string | подсказка UI («тяжёлый день, не совмещать с бегом») |

Пример недели (strength, 4 тренировки):

```text
Пн → «День A — Ноги»      workout   (якорь)
Вт → кардио 30 мин        cardio
Ср → «День B — Жим»       workout   (якорь)
Чт → отдых                rest
Пт → «День C — Тяга»      workout
Сб → «День D — Плечи»     optional
Вс → отдых                rest
```

**День плана (`SProgram_Day` / `program_days`).**

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор дня |
| `programId` | string | программа |
| `title` | string | «День A — Ноги» |
| `kind` | enum | `workout`, `rest`, `cardio`, `mobility` |
| `focus` | enum[] | целевые группы мышц: `legs`, `push`, `pull`, `core`, `fullBody` |
| `estimatedMinutes` | int | оценка длительности для UI |
| `orderIndex` | int | порядок в списке дней и в ротации |
| `note` | string | примечание к дню |
| `sourceDayId` | string \| null | `plan_days.id` шаблона, из которого сделан снимок |

Операции над днями: добавить день, дублировать («День A (копия)»), удалить
(слот недели следует перевести в `rest`), переименовать, изменить состав,
задать набор упражнений заново. Изменение состава дня при активной программе
разрешено, но инкрементирует `revision`: будущие недели считаются по новой
версии, а факты прошлых недель остаются при своих снимках предписаний (3.5).

### 3.5. Предписание упражнения (`SDay_Exercise` / `program_day_exercises`)

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор строки |
| `programDayId` | string | день плана |
| `exerciseId` | string | ссылка на `exercises` |
| `orderIndex` | int ≥0 | порядок в дне, задаёт drag&drop |
| `sets` | int 1–20 | плановое число рабочих подходов |
| `repsMin`, `repsMax` | int | диапазон повторов («8–12»); равны для фиксированных |
| `weightMode` | enum | `fixed` (по `targetWeightKg`), `percentOf1RM`, `byFeel`, `fromLastSession`, `bodyWeight` |
| `targetWeightKg` | number \| null | при `fixed` |
| `percentOf1RM` | number \| null | при `percentOf1RM` («80 % 1ПМ») |
| `rpeTarget` | number \| null | целевой RPE для подхода (5–10, шаг 0,5) |
| `restSeconds` | int | отдых между подходами (по умолчанию из настроек, issue 32) |
| `tempo` | string \| null | нотация темпа (`3-1-1-0`), опционально |
| `supersetGroup` | string \| null | метка группы суперсета: строки с одинаковой меткой идут парой |
| `warmupSets` | int ≥0 | число разминочных подходов (не входят в тоннаж) |
| `progressionRule` | `SProgression_Rule` \| null | как двигать вес по неделям/при успехе |
| `substitutionIds` | string[] | разрешённые замены (нет штанги — гантели) |
| `isOptional` | bool | можно пропустить без потери выполнения дня |
| `note` | string | техника, напоминание |

**Правило прогрессии (`SProgression_Rule`)** — компактная структура внутри
предписания:

| Поле | Тип | Назначение |
|---|---|---|
| `type` | enum | `linearWeight` (+2,5 кг при выполнении всех подходов), `doubleProgression` (сначала верх диапазона повторов, затем вес), `percentPerWeek` (+2 %/нед.), `manual` |
| `incrementKg` | number \| null | шаг веса для линеек (`2.5`, `1.25`, `5`) |
| `triggerSets`, `triggerRepsMin` | int \| null | условие срабатывания («все подходы ≥ 10 повторов») |
| `maxRpe` | number \| null | не повышать вес, если RPE выше лимита |
| `deloadEveryWeeks` | int \| null | разгрузка каждые N недель (вес −40 %) |

Движок правил применяет прогрессию при открытии тренировки дня: UI получает
`targetWeightKg` как **рекомендацию** (`suggestedWeight` в
`mock-data-contract.md` §2.3) и подпись подхода («вчера было 60 кг × 8»).

### 3.6. Правила программы (`SProgram_Rule` / `program_rules`)

Правило — измеримая директива, которую пользователь обязуется соблюдать в
рамках программы. Оно отвечает на три вопроса: **что** (метрика), **сколько**
(цель и единица), **как проверяем** (источник и периодичность).

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор правила |
| `programId` | string | программа |
| `category` | enum | `nutrition`, `training`, `recovery`, `lifestyle`, `technique` |
| `code` | enum | типовой код правила (см. каталог ниже) или `custom` |
| `title` | string | текст правила для UI («Белок не ниже 1,8 г/кг») |
| `metric` | enum | `proteinGrams`, `caloriesKcal`, `waterMl`, `sleepHours`, `stepCount`, `bodyWeightKg`, `maxRpe`, `restHoursBetweenSessions`, `alcoholUnits`, `custom` |
| `periodicity` | enum | `perDay`, `perWeek`, `perWorkout`, `once` |
| `target` | `SRule_Target` | целевое значение: `min`, `max` или `exact` + `unit` |
| `appliesTo` | enum | `allDays`, `trainingDays`, `restDays`, `customDays` (+ `days[]`) |
| `checkSource` | enum | `selfReport` (пользователь отмечает), `computedFromSets` (из подходов), `computedFromProfile` (из веса тела), `computedFromSessions` (из дат/длительностей), `computedFromLog` (из дневника питания, §3.10), `mixed` |
| `enforcement` | enum | `soft` (влияет на adherence) или `hard` (блокирует закрытие дня/тренировки) |
| `activeFrom`, `activeTo` | date \| null | период действия правила внутри программы |
| `displayUnit` | enum | `g`, `gPerKg`, `kcal`, `ml`, `hours`, `count`, `rpe`, `units` |
| `note` | string | источник правила, пояснение тренера |

**Каталог типовых правил** (стартовый набор для UI «Добавить правило»):

| `code` | Категория | Метрика / периодичность | Значение по умолчанию | Источник проверки |
|---|---|---|---|---|
| `protein` | nutrition | `proteinGrams` / `perDay` | 1,8 г на кг веса тела | `computedFromProfile` + ручная отметка факта; `computedFromLog` при включённом дневнике (§3.10) |
| `calories` | nutrition | `caloriesKcal` / `perDay` | ±10 % от расчётной нормы | `selfReport` |
| `water` | nutrition | `waterMl` / `perDay` | 30 мл на кг веса | `selfReport` |
| `sleep` | recovery | `sleepHours` / `perDay` | 7–9 ч | `selfReport` |
| `steps` | lifestyle | `stepCount` / `perDay` | 8 000 шагов | `selfReport` (в будущем — платформенный шагомер) |
| `maxRpe` | training | `maxRpe` / `perWorkout` | не выше RPE 8 на базовых | `computedFromSets` |
| `restBetweenSessions` | training | `restHoursBetweenSessions` / `perDay` | ≥ 24 ч отдыха между силовыми днями одной группы | `computedFromSessions` |
| `progressionDiscipline` | training | `custom` / `perWorkout` | +2,5 кг только при выполнении всех подходов | `computedFromSets` |
| `bodyWeightControl` | recovery | `bodyWeightKg` / `perWeek` | взвешивание 1 раз в неделю | `selfReport` + замер |

Правила `maxRpe`, `restBetweenSessions`, `progressionDiscipline` **не требуют
ручных отметок** — они вычисляются из фактов тренировок. Это важно для
сценария «правила сами себя проверяют»: пользователь открывает статистику и
видит, что он нарушил лимит RPE три раза за неделю, без каких-либо галочек.

### 3.7. Отметка правила (`SRule_Checkin` / `rule_checkins`)

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор отметки |
| `ruleId` | string | правило |
| `programId` | string | программа (дублируется для быстрых агрегатов) |
| `date` | date | день, к которому относится отметка (для `perWeek` — дата начала недели) |
| `value` | number \| null | фактическое значение (например, 145 г белка) |
| `unit` | enum | единица значения |
| `state` | enum | `done`, `failed`, `skipped`, `partial`, `unknown` |
| `source` | enum | `manual`, `computed`, `imported` |
| `sessionId` | string \| null | тренировка-источник для `computedFromSets` |
| `mealLogId` | string \| null | запись дневника питания как источник значения (резерв, §3.10); при заполнении значение считается производным от дневника |
| `note` | string | короткий комментарий |
| `createdAt`, `updatedAt` | ISO 8601 | служебные метки |

Инварианты отметок: одна отметка на пару `ruleId + date` для `perDay`/
`perWeek` (повторная запись — обновление значения); `source = computed`
не редактируется руками — ручная правка создаёт новую отметку с
`source = manual` и переопределяет расчётную для этого дня.

### 3.8. Факты: сессия и подход

**Сессия (`SWorkout_Session` / `workouts`)** — расширение уже принятых ролей
(`mock-data-contract.md` §2.3, §2.7):

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор |
| `userId` | string | владелец |
| `programId` | string \| null | программа; `null` — тренировка вне программы (соло) |
| `programDayId` | string \| null | день плана |
| `plannedDate`, `plannedWeekIndex` | date, int \| null | по какому плану и какой неделе шла сессия |
| `date` | date | фактическая дата выполнения |
| `startedAt`, `completedAt` | ISO 8601 | границы |
| `durationSeconds` | int \| null | активное время тренировки |
| `state` | enum | `draft`, `completed`, `cancelled` (уже принято) |
| `deviation` | enum \| null | `asPlanned`, `partial`, `substituted`, `extraDay`, `movedDay` |
| `exerciseCount`, `setCount` | int | сводка для списков истории |
| `tonnageKg` | number | сумма `weightKg × reps` по рабочим подходам |
| `avgRpe` | number \| null | средний RPE рабочих подходов |
| `programRevision` | int \| null | версия структуры программы на момент сессии |
| `note` | string | заметка к тренировке |
| `syncState` | enum | `synced`, `local`, `syncing`, `offline` |

**Подход (`SSet_Log` / `sets`).**

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор |
| `sessionId` | string | сессия |
| `dayExerciseId` | string \| null | строка предписания, по которой выполнялся подход |
| `exerciseId` | string | упражнение (дублируется: замена упражнения сохраняет факт) |
| `setNumber` | int ≥1 | номер подхода |
| `isWarmup` | bool | разминочный (не в тоннаж, не в рекорды) |
| `weightKg`, `reps` | number, int | факт |
| `rpe` | number \| null | `null`/`0` — не введён |
| `targetWeightKg`, `targetReps` | number \| null | **снимок** рекомендации на момент тренировки |
| `done` | bool | подход зачтён |
| `note` | string | комментарий |

Снимок предписания в факте (`targetWeightKg`, `targetReps`, `programRevision`)
— обязательное требование: он позволяет отделить «пользователь не выполнил
план» от «план поменялся», и делает статистику воспроизводимой.

**Тоннаж** считается только по `done = true` и `isWarmup = false`; подход с
`reps = 0` не зачитывается. Правка завершённой тренировки — только заметки;
изменение фактических подходов задним числом допускается лишь через
`correctionOfSessionId` (новая запись со ссылкой на исправляемую) — так
история и рекорды не «переписываются молча».

### 3.9. Журнал изменений программы (`SProgram_Revision` / `program_revisions`)

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | идентификатор |
| `programId` | string | программа |
| `revision` | int | номер версии |
| `changedAt` | ISO 8601 | когда |
| `reason` | enum | `goal`, `term`, `schedule`, `days`, `rules`, `exercisePlan`, `state` |
| `summary` | string | человекочитаемое описание («+2 недели», «День A: −1 упражнение») |
| `snapshot` | JSON | компактный снимок изменённой части (для отката и объяснения статистики) |

Журнал нужен для трёх задач: объяснить пользователю, почему статистика
изменилась («план был продлён на 2 недели»); корректно считать adherence по
плану, действовавшему на конкретной неделе; дать основу для отката правки.

### 3.10. Резерв: дневник питания (post-MVP)

Принятое решение по питанию — **гибрид**: в MVP правило хранит цель и отметку
факта (§3.6, §3.7), но модель уже резервирует ссылку `mealLogId`, поэтому
переход к полному дневнику не потребует менять формат отметок и статистику.

| Сущность (резерв) | Поля | Назначение |
|---|---|---|
| `SNutrition_Entry` / `nutrition_entries` | `id`, `userId`, `date`, `mealType` (`breakfast`, `lunch`, `dinner`, `snack`), `foodId` \| `customTitle`, `portionGrams`, `proteinG`, `fatG`, `carbsG`, `caloriesKcal`, `source` (`manual`, `barcode`, `preset`), `syncState` | одна съеденная позиция |
| `SNutrition_Day` (производное) | `date`, `proteinG`, `fatG`, `carbsG`, `caloriesKcal`, `entriesCount` | дневной итог для правил и статистики |

Как дневник связан с правилами:

- `checkSource = computedFromLog`: значение правила за день — сумма по
  `nutrition_entries`; `rule_checkins.mealLogId` указывает на агрегирующую
  запись дня;
- ручная отметка приоритетнее: `source = manual` перекрывает `computed`, а
  правка значения не меняет записи дневника (инвариант 25);
- формулы статистики (§5.1, §5.2) не меняются: `avgProteinGramsPerDay`
  считается из отметок независимо от источника значения;
- в UI MVP блок «Правила» показывает норму и поле ввода; при включении
  дневника то же поле становится «посчитано из дневника» с кнопкой «Изменить».

Что **не** входит в резерв: база продуктов, сканер штрихкодов, рецепты,
распознавание по фото — отдельные подсистемы, не влияющие на модель программы.
Таблицы резерва создаются в схеме сразу (пустыми, §8), UI включается отдельным
issue после MVP.

## 4. Правила целостности

**Программа и расписание**

1. У пользователя не более одной программы в состоянии `active`; остальные —
   `draft`, `paused`, `completed`, `cancelled`, `archived`.
2. `scheduleKind = weekday` → ровно 7 слотов, `dayOfWeek` уникален и лежит
   в 1–7; минимум один слот с `kind = workout`.
3. `scheduleKind = rotation` → слоты нумеруются `rotationIndex` от 1 без
   пропусков; длина цикла равна числу слотов.
4. `daysPerWeek` = число слотов `workout` + `optional`, всегда производное
   значение (не редактируется напрямую).
5. День плана с `kind = workout` содержит минимум одну строку
   `program_day_exercises`; удаление последнего упражнения переводит день
   в `rest` либо запрещено (решение UI: подтверждение).
6. `orderIndex` уникален внутри дня; `setNumber` уникален внутри
   `sessionId + exerciseId`.
7. Слот не может ссылаться на день плана другой программы.

**Цель, срок, правила**

8. `goalTargets` не бывает пустым при `state = active`, если `goal` требует
   измеримого результата (`fatLoss`, `strength`); для `fitness` допустим
   пустой список.
9. `targetValue` при `direction = decrease` меньше `startValue`; при
   `increase` — больше; при `maintain` — равно (в пределах допуска).
10. Значение правила в метрике «на кг веса» (`protein`, `water`) хранится как
    цель в граммах/мл, а пересчёт `× bodyWeightKg` выполняется при показе —
    иначе правило «поедет» после изменения веса.
11. `enforcement = hard` запрещено для правил `selfReport`, которые нельзя
    проверить объективно (сон, шаги) — только предупреждение.
12. Активное правило не может быть удалено, только деактивировано
    (`activeTo = сегодня`) либо перенесено в архив программы.

**Факты и статистика**

13. `state = completed` требует `completedAt` и хотя бы одного подхода с
    `done = true`; иначе сессия остаётся `draft` (пустая тренировка не
    попадает в историю и статистику).
14. `programId` завершённой сессии неизменяем; перенос сессии в другую
    программу запрещён (используется `correctionOfSessionId`).
15. Статистика — **чистая функция** от фактов, замеров и текущей структуры
    программы: при одинаковых входах результат одинаков. Кэш `program_stats`
    допускается, но обязан быть воспроизводимым при полном пересчёте.
16. Изменение структуры программы не переписывает статистику прошлых недель:
    adherence и план/факт считаются по `programRevision`, действовавшей на
    дату сессии.
17. Дни без сессии в прошлом (после `actualStartDate` и до сегодня) считаются
    пропусками только для слотов `workout` и `isAnchor = true`; слоты
    `optional` — не пропуск, а «необязательный день».
18. Сессии вне программы (`programId = null`) входят в `Lifetime_Stats`, но не
    в `Program_Stats` ни одной программы.
19. Одна отметка правила на `ruleId + date`; расчётная отметка не
    редактируется вручную.
20. Замеры тела (`bodyWeightKg`, `measurementCm`) хранятся отдельной
    последовательностью измерений, а не только полем профиля: иначе
    невозможно построить график и посчитать дельту за программу.

**Данные и локализация**

21. Единицы хранения — метрические (кг, см, мл, ч, ккал); имперские единицы —
    задача отображения (issue 32).
22. Enum и `code` — ASCII, стабильные; локализованный текст только в полях
    `title`/`note`, которые пользователь может править.
23. День принадлежит **локальной** дате пользователя; неделя начинается в
    понедельник (ISO 8601). Смена часового пояса не перезаписывает даты
    уже сохранённых фактов.
24. Программа в `archived`/`completed` read-only по структуре, но правила
    отметок и заметки доступны для ретроспективы ограниченное время
    (по умолчанию — конец недели завершения).
25. Если у отметки заполнен `mealLogId`, её значение считается производным от
    дневника питания (§3.10); ручная правка создаёт перекрывающую отметку
    `source = manual` и не изменяет записи дневника.

### 5.2. Формулы

```text
tonnageKg(сессия)      = Σ (weightKg × reps)      для done = true и isWarmup = false
tonnageKg(период)      = Σ tonnageKg(сессии периода)

e1RM(подход)           = weightKg × (1 + reps / 30)          // формула Эпли
workingWeight(упр.)    = max(weightKg) среди done-подходов, isWarmup = false
progressPercent(упр.)  = (workingWeight_тек − workingWeight_старт) / workingWeight_старт × 100

adherencePercent       = completedSessions / plannedSessions × 100
weekAdherence          = completed(weekIndex) / planned(weekIndex) × 100

avgRpe                 = Σ rpe / count(rpe ≠ null)
setsPerMuscleGroup     = Σ подходов, где exercises.muscleGroup = G, за неделю

proteinTargetGrams     = coefficientGramsPerKg × bodyWeightKg   // пересчёт при показе
proteinAdherence       = Σ(день, где value ≥ proteinTargetGrams) / days × 100

weeklyFrequency        = completedSessions / (длительность периода в неделях)   // KPI «Частота 3,1»
goalProgressPercent    = (current − start) / (target − start) × 100             // direction = increase
                         (start − current) / (start − target) × 100             // direction = decrease
```

Все формулы детерминированы и считаются на локальных данных; серверные KPI
(если появятся, issue 35) обязаны совпадать с ними либо быть помечены как
серверные — «две правды» в одном экране недопустимы.

### 5.3. Общая статистика (`SLifetime_Stats`)

Считается по **всем** программам пользователя (включая завершённые, отменённые
и соло-тренировки) — это «витрина прогресса за всё время».

| Блок | Метрика | Определение |
|---|---|---|
| Итоги | `totalPrograms`, `completedPrograms`, `cancelledPrograms` | по `state` |
| | `totalSessions`, `totalSets`, `totalReps` | счётчики фактов |
| | `lifetimeTonnageKg` | Σ по всем сессиям |
| | `lifetimeDurationMinutes` | Σ длительности |
| | `firstSessionDate`, `lastSessionDate` | границы истории |
| | `activeDaysCount` | число дней с хотя бы одной завершённой сессией |
| Регулярность | `weeksWithSessions`, `longestStreakWeeks`, `currentStreakWeeks` | по неделям ISO |
| | `avgSessionsPerWeek` | `totalSessions / weeksSince(firstSessionDate)` |
| | `regularityHeatmap[]` | неделя → число тренировок (роль `workoutCount` уже принята в §2.2 контракта) |
| Сила | `records[]` | личные рекорды по упражнениям: значение, дата, `programId`, `sessionId` |
| | `bestE1rmByExercise[]` | e1RM-максимум за всё время и когда достигнут |
| | `workingWeightTrend[]` | прогресс веса по ключевым упражнениям за всё время |
| Тело | `bodyWeightSeries[]`, `measurementSeries[]` | все замеры по датам |
| | `bodyWeightTotalDeltaKg` | первое → последнее измерение |
| Правила | `ruleStreaksByCode[]` | лучшая серия по каждому типовому правилу («белок: 24 дня подряд») |
| | `avgProteinPerKgByProgram[]` | сравнение питания между программами |
| Программы | `programSummaries[]` | по каждой программе: `title`, `goal`, `term`, `sessions`, `tonnageKg`, `adherencePercent`, `bodyWeightDeltaKg`, `keyLiftDeltaKg` — основа экрана сравнения |
| | `bestProgramId` | лучший по выбранной метрике (пользователь переключает метрику) |

Сравнение программ важно методически: программа сравнима только по метрикам,
посчитанным одинаково (сессии, тоннаж, adherence, дельта веса тела и ключевого
упражнения); рост тоннажа между разными целями (`fatLoss` против `strength`)
в UI не подаётся как «прогресс» без нормализации на длительность и число
тренировок.

### 5.4. Расчёт, кэш и инвалидация

- **Source of truth** — только факты: `workouts`, `sets`, `rule_checkins`,
  замеры тела, структура программы и её ревизии. Никаких «сохранённых итогов»
  как первичных данных.
- **Кэш**: таблицы `program_stats` (строка на программу) и `lifetime_stats`
  (одна строка на пользователя) с `computedAt` и `programRevision`.
  Инвалидация: любая запись факта, правка правила/цели/расписания, завершение
  программы, добавление замера — помечает кэш устаревшим.
- **Пересчёт**: инкрементально по затронутой неделе при обычной записи; полный
  пересчёт — при `revision++`, смене периода, ручном действии в DevPanel и в
  тестах. Полный пересчёт обязан давать те же числа, что инкрементальный
  (тест-инвариант).
- **Место расчёта**: `AsProgress_Calculator` (расширение issue 25) —
  тоннаж, частота, рабочий вес, e1RM, рекорды, дельты, план/факт;
  `AsRule_Engine` — оценка правил (в первую очередь расчётных) и подсчёт
  adherence. Оба сервиса — чистые функции над структурами, без QML и SQL.
- **Сервер**: когда появится контракт (issue 35), серверная статистика
  дублирует локальную; локальные расчёты остаются источником для офлайна.

### 5.5. Периоды, часовые пояса, точность

- «Сегодня» — локальная дата устройства; неделя — с понедельника (ISO 8601).
- Программа привязывается к `actualStartDate`, а не к календарной неделе:
  первая и последняя недели могут быть короче полных.
- `weekIndex` считается от `actualStartDate` (`1…N`), поэтому «неделя 3» в
  программе не обязана совпадать с календарной неделей.
- Дни отдыха и незапланированные тренировки не искажают adherence: в знаменателе
  только слоты, которые программа действительно ожидала.
- Округление: вес — до 0,5 кг при вводе, проценты — до целых при показе,
  тоннаж — до 0,1 т в текстах (`tonnageText`), в расчётах — без округления.
- Метрики без данных (`plannedSessions = 0`) возвращают `null`, а не `0`:
  UI различает «нечего считать» и «ноль выполнено».

## 6. Сценарии использования

### UC-1. Взять программу из каталога

- **Актор:** пользователь (авторизован или гость с локальной программой).
- **Предусловие:** активной программы нет либо пользователь создаёт новую.
- **Поток:** «Планы» → карточка плана (`planDetails`) → «Взять этот план» →
  форма: стартовая дата, срок (по умолчанию из шаблона), дни недели
  (подставить предлагаемые слоты шаблона), цель, вес тела для правил →
  «Создать программу».
- **Данные:** создаётся `SProgram` со `sourceKind = template`,
  `sourceTemplateId = plans.id`; копируются `plan_days` → `program_days` и
  `day_exercises` → `program_day_exercises`; шаблонные правила (если есть)
  копируются как `program_rules`; `state = draft`, `revision = 1`.
- **Результат:** программа видна в «Сегодня»/«Моей программе», шаблон в
  каталоге не изменился.
- **Крайние случаи:** два пользователя взяли один шаблон — правки одного не
  видны другому; взят план, слоты которого конфликтуют с выбранными днями —
  UI предлагает ближайшее неконфликтующее распределение.

### UC-2. Собрать программу с нуля или скопировать и изменить

- **Поток:** «Мои программы» → «Создать» → выбрать: «С нуля» (`scratch`) или
  «Скопировать и изменить» из уже взятой (`copy`) → шаг 1: цель и срок →
  шаг 2: дни недели и дни плана → шаг 3: упражнения дней → шаг 4: правила →
  «Начать программу».
- **Данные:** `sourceKind = scratch | copy`; для `copy` — полный снимок
  структуры с новым `id` (в том числе при копировании собственной программы).
- **Результат:** у пользователя одна `active` программа; предыдущая переходит
  в `paused` или `archived` по выбору пользователя в диалоге.

### UC-3. Индивидуальный план для каждого дня недели

- **Актор:** пользователь, настраивающий расписание и состав дней.
- **Поток:** «Моя программа» → «Расписание» → таблица Пн…Вс, где на каждый
  день назначается день плана, отдых, кардио или мобилити; «Добавить день
  плана» → имя, фокус, оценка времени; состав дня — добавление упражнений из
  каталога, drag&drop для порядка, указание подходов/повторов/веса/RPE/отдыха,
  суперсеты, дублирование упражнения, замена (`substitutionIds`).
- **Данные:** правки `program_schedule`, `program_days`,
  `program_day_exercises`; при активной программе — `revision++` и запись в
  `program_revisions` с `reason = schedule | days | exercisePlan`.
- **Результат:** каждый день недели имеет собственный настраиваемый план; в
  «Сегодня» отображается план текущего дня недели (или следующего по ротации).
- **Пример:** Пн — ноги (5 упражнений), Вт — кардио 30 мин, Ср — жим, Чт —
  отдых, Пт — тяга, Сб — плечи (optional), Вс — отдых.
- **Крайние случаи:** изменение дня, который уже выполнялся на этой неделе, не
  переписывает факты (у них остался снимок предписания); удаление дня, занятого
  в расписании, требует переназначения слота.

### UC-4. Цель, срок и правила программы

- **Поток:** «Моя программа» → «Цель и правила» → выбор цели → добавление
  измеримых целей (вес тела 78 → 74 кг, жим 100 кг × 5, обхват пояса −3 см,
  частота 3/нед.) → срок (8/12/24 недели или «до результата») → блок правил:
  выбрать из каталога (`protein`, `water`, `sleep`, `steps`, `maxRpe`,
  `restBetweenSessions`) и задать значения; «Добавить своё правило» для
  `custom`.
- **Данные:** `SProgram.goal`, `goalTargets[]`, `term`, `program_rules[]`;
  расчётные нормы («1,8 г/кг» → «143 г») вычисляются при показе по текущему
  весу тела, а не сохраняются числом.
- **Результат:** «Сегодня» показывает план дня + компактный чек-лист правил;
  «Статистика» получает раздел «Правила».
- **Крайние случаи:** цель `decrease` при `targetValue > startValue` —
  валидация не пропускает; правило `protein` без известного веса тела требует
  сначала ввести замер.

### UC-5. Тренировка по плану дня

- **Поток:** «Сегодня» → hero-карточка дня (день недели, неделя `X из N`,
  число упражнений) → «Начать тренировку» → оверлей записи: упражнение за
  упражнением, подходы с рекомендованным весом и диапазоном повторов → ввод
  факта (вес, повторы, RPE, заметка) → «Готово» → таймер отдыха →
  переход к следующему подходу → «Завершить тренировку» → сводка: тоннаж,
  время, число подходов, выполнение плана.
- **Данные:** `SWorkout_Session` (`state = draft` → `completed`, `deviation`,
  `tonnageKg`); `SSet_Log` со снимком `targetWeightKg/targetReps`;
  `isWarmup` для разминки; по завершении — инвалидация статистики и
  пересчёт рекордов.
- **Результат:** сессия в истории, обновлены `Program_Stats` и
  `Lifetime_Stats`, выполнены расчётные правила (`maxRpe`,
  `progressionDiscipline`, `restBetweenSessions`).
- **Крайние случаи:** приложение закрыто в середине — `draft` восстанавливается
  (issue 27); тренировка растянулась на сутки — датой считается дата старта;
  все подходы пропущены — сессия не завершается «пустой» (инвариант 13).

### UC-6. Отметки правил в течение дня

- **Поток:** «Сегодня» → блок «Правила» → список норм дня («белок 143 г»,
  «вода 2,6 л», «сон 7–9 ч») → ввод фактического значения или «Выполнено» /
  «Пропущено» / «Не удалось» → вечерняя сводка «выполнено 2 из 3».
- **Данные:** `SRule_Checkin` (`source = manual`), для расчётных правил —
  записи с `source = computed` без участия пользователя; при включённом
  дневнике питания значение приходит из `nutrition_entries` (`source =
  computed`, ссылка `mealLogId`, §3.10).
- **Результат:** дневная и недельная адхеренция правил, серии («белок: 12 дней
  подряд»), вклад в `ruleAdherencePercent`.
- **Крайние случаи:** правило с `enforcement = hard` (`maxRpe` в силовой
  программе) предупреждает при попытке закрыть тренировку с нарушением;
  повторный ввод значения за тот же день обновляет отметку, а не создаёт вторую.

### UC-7. Перенос, пропуск и замена

- **Актор:** пользователь, у которого сорвался график.
- **Поток:** «Сегодня» → «Перенести на…» → выбор даты → `deviation = movedDay`;
  либо пропуск дня → неделя отмечается как неполная; либо замена упражнения
  на `substitutionIds` → `deviation = substituted`; либо «Дополнительная
  тренировка» вне расписания → `deviation = extraDay`.
- **Данные:** правки `plannedDate`, `deviation`; сам факт остаётся в истории.
- **Результат:** adherence показывает `movedSessions`, `extraSessions`;
  `missedSessions` не «сгорают», а отображаются отдельно, чтобы не путать
  перенос и срыв.
- **Крайние случаи:** перенос на прошедшую дату запрещён; день с `isAnchor`
  переносится только с подтверждением и предупреждением о нагрузке.

### UC-8. Изменение программы на ходу

- **Поток:** пользователь решает увеличить срок, сменить цель, добавить день
  или заменить упражнение в середине программы.
- **Данные:** `revision++`, запись в `program_revisions`; изменения действуют
  начиная с даты правки.
- **Результат:** статистика честно разделена: прошлые недели считаются по
  прежней ревизии, будущие — по новой; в «Статистике» есть пояснение
  («план продлён на 2 недели 15.10»).
- **Крайние случаи:** смена цели обнуляет только отображение `goalProgress`,
  но не историю; понижение срока ниже фактически прошедших недель требует
  подтверждения и не удаляет факты.

### UC-9. Пауза, завершение и архив

- **Поток:** «Моя программа» → «Пауза» (отпуск/болезнь) → «Продолжить»;
  при достижении цели или конца срока — «Завершить», с опциональным
  «почему досрочно» → программа уходит в `completed`/`cancelled` →
  автоматически в `archived` через N дней.
- **Данные:** `state`, `actualEndDate`, финальный пересчёт
  `SProgram_Stats` → строка в `programSummaries[]` лайфтайма.
- **Результат:** программа видна в «Мои программы» со сводкой и в общей
  статистике; структура read-only, отметки правил доступны до конца недели
  завершения.
- **Крайние случаи:** пауза не рвёт `currentStreakWeeks` (недели паузы
  исключаются из знаменателя); отменённая программа не считается «лучшей», но
  её тоннаж входит в лайфтайм.

### UC-10. Статистика активной программы

- **Поток:** «Моя программа» → «Статистика»: KPI недели (тоннаж, частота,
  adherence), график тоннажа по неделям, график рабочего веса ключевых
  упражнений, блок «Цели» с прогрессом каждого `Goal_Target`, блок «Правила»
  (белок/вода/сон, серии, нарушения `maxRpe`), блок «Тело» (вес, обхваты),
  список рекордов программы.
- **Данные:** чтение `SProgram_Stats` (+ `weekAdherence[]`,
  `tonnageByWeek[]`, `ruleStats[]`); при устаревшем кэше — пересчёт.
- **Результат:** пользователь понимает, где именно отстаёт (объём? питание?
  регулярность?) и что делать на следующей неделе.
- **Крайние случаи:** программа только началась — вместо нулей показываются
  состояния «данных пока нет» (`null`-метрики); дельта «плюс» по весу тела при
  цели «похудение» подсвечивается предупреждением, а не успехом.

### UC-11. Общая статистика по всем пройденным программам

- **Поток:** «Профиль» → «Прогресс» → переключатель «Программа / Всё время»:
  лайфтайм-итоги (тренировок всего, тоннаж за всё время, недель занимаюсь,
  текущая и лучшая серия), heatmap регулярности, графики по ключевым
  упражнениям, список рекордов с указанием программы-источника, таблица
  сравнения программ (`programSummaries[]`: срок, тренировок, тоннаж,
  adherence, Δ веса тела, Δ ключевого упражнения), «Лучшая программа» по
  выбранной метрике.
- **Данные:** `SLifetime_Stats` (агрегат по всем `state`, включая
  `cancelled`, `archived` и соло-сессии).
- **Результат:** пользователь видит долгосрочный прогресс и может сравнить
  программы между собой и с соло-тренировками.
- **Крайние случаи:** сравнение программ с разной длительностью — метрики
  нормализуются (тоннаж/нед., adherence, а не абсолютный тоннаж);
  единственная программа — блоки сравнения скрываются, а не показывают «1».

### UC-12. Офлайн, синхронизация и восстановление

- **Поток:** пользователь тренируется без сети: программа, расписание и
  правила доступны из локальной SQLite (снимок), тренировка пишется локально
  (`syncState = local`), статистика считается локально; при появлении сети
  факты уходят наверх (issue 34), при конфликте структуры (серверная версия
  программы новее) — приоритет отдаётся фактам пользователя, структура
  подтягивается с уведомлением.
- **Данные:** `sync_outbox` (уже принят, issue 9), `syncState` у программы,
  сессий и правок; журнал ревизий — основа для merge структуры.
- **Результат:** никакой сценарий не требует сети для заполнения дня и
  просмотра статистики.
- **Крайние случаи:** два устройства заполнили один день — обе сессии
  сохраняются (это не конфликт, а два факта), adherence считается по числу
  завершённых слотов, а не по числу записей.

### UC-13. Тренировка вне программы

- **Поток:** пользователь идёт в зал без плана → «Сегодня» → «Свободная
  тренировка» → добавляет упражнения вручную → завершает.
- **Данные:** `SWorkout_Session` с `programId = null`, `deviation = null`.
- **Результат:** тренировка входит в историю и в **общую** статистику
  (тоннаж, частота, рекорды, heatmap), но не в `SProgram_Stats` активной
  программы; в статистике программы такие сессии показываются отдельной
  сноской «вне программы: 2».
- **Крайние случаи:** если открыта активная программа и день совпадает по
  группе мышц, UI предлагает «зачесть как день плана» — тогда
  пользователь выбирает `programDayId`, и сессия становится частью программы.

## 8. Черновик схемы SQLite (расширение issue 22)

```text
programs(id PK, user_id, title, source_kind, source_template_id,
         goal, level, schedule_kind, state, revision,
         start_date, actual_start_date, weeks_total, extended_weeks, term_mode,
         end_date_generated, created_at, updated_at, sync_state, note)

goal_targets(id PK, program_id FK, metric, exercise_id, measurement_key,
             unit, start_value, target_value, target_weight_kg, target_reps,
             direction, target_date, state)

program_schedule(id PK, program_id FK, day_of_week, rotation_index,
                 program_day_id FK, kind, is_anchor, note)

program_days(id PK, program_id FK, title, kind, focus, estimated_minutes,
             order_index, source_day_id, note)

program_day_exercises(id PK, program_day_id FK, exercise_id FK, order_index,
                      sets, reps_min, reps_max, weight_mode, target_weight_kg,
                      percent_of_1rm, rpe_target, rest_seconds, tempo,
                      superset_group, warmup_sets, progression_json,
                      substitution_ids, is_optional, note)

program_rules(id PK, program_id FK, category, code, title, metric, periodicity,
              target_min, target_max, target_exact, target_unit, applies_to,
              applies_days, check_source, enforcement, active_from, active_to,
              display_unit, note)

rule_checkins(id PK, rule_id FK, program_id FK, date, value, unit, state,
              source, session_id, meal_log_id, note, created_at, updated_at)

program_revisions(id PK, program_id FK, revision, changed_at, reason,
                  summary, snapshot_json)

workouts(id PK, user_id, program_id FK NULL, program_day_id FK NULL,
         planned_date, planned_week_index, date, started_at, completed_at,
         duration_seconds, state, deviation, exercise_count, set_count,
         tonnage_kg, avg_rpe, program_revision, correction_of_session_id,
         note, sync_state)

sets(id PK, session_id FK, day_exercise_id FK NULL, exercise_id FK,
     set_number, is_warmup, weight_kg, reps, rpe, target_weight_kg,
     target_reps, done, note)

body_measurements(id PK, user_id, date, weight_kg, chest_cm, waist_cm,
                  hip_cm, arm_cm, thigh_cm)

-- резерв §3.10: создаются пустыми, UI — post-MVP
nutrition_entries(id PK, user_id, date, meal_type, food_id, custom_title,
                  portion_grams, protein_g, fat_g, carbs_g, calories_kcal,
                  source, sync_state)
nutrition_day_totals(user_id, date, protein_g, fat_g, carbs_g, calories_kcal,
                     entries_count, PK(user_id, date))

program_stats(program_id PK, computed_at, program_revision, payload_json)
lifetime_stats(user_id PK, computed_at, payload_json)
```

Замечания к схеме:

- **Реализовано в срезе W1** (schema v2, `AsSql_Database::Create_Schema_V2`,
  тесты `tst_Sql_Database`): все таблицы этого списка, инвариант «одна активная
  программа» (частичный уникальный индекс) и минимальный `exercises` для FK.
  Остаток issue 22 — каталог `plans`/`plan_days`/`day_exercises` и seed 1:1 с
  mock — миграция v3 (фаза B). `target_weight_kg` / `target_reps` в
  `goal_targets` — цель-«упражнение» (`repsAtWeight`, §3.2).
- `plans` / `plan_days` / `day_exercises` остаются **каталогом** (issue 22);
  пользовательские структуры живут в `program_*`; префикс снимает путаницу
  между шаблоном и программой.
- Индексы: `sets(session_id)`, `workouts(program_id, date)`,
  `rule_checkins(rule_id, date)`, `program_schedule(program_id, day_of_week)`,
  `nutrition_entries(user_id, date)` (резерв).
- `progression_json` и `payload_json` — сериализованные структуры: они не
  участвуют в SQL-фильтрации, живут как JSON-строки (Qt `QJsonDocument`).
- `end_date_generated` — материализованное производное поле для сортировок,
  пересчитывается в одном месте (репозиторий программы).
- Замеры тела — отдельная таблица, а не поле профиля (инвариант 20).

`04-roadmap.md` §3): схема (22) → репозитории (23) → модели (24) → сервисы
домена (25) → ViewModels (26) → экраны 41–44 → сеть (34/35). Экраны программы
на mock не строятся: они читают SQLite через `Avm_*`; «Сегодня» (27), «Планы»
(28) и «Профиль» (31) подключаются к данным среза. До появления серверного
контракта вся модель считается локальной и помечается **assumed** там, где
речь о серверных полях.

## 10. Открытые вопросы

**Продукт**

1. Одна активная программа или несколько параллельных (силовая + бег)?
   Документ исходит из «одной активной».
2. Пропущенный день: перенос (мягкий adherence) или срыв? Нужна ли
   настраиваемая политика «переносить непроведённые дни»?
3. Порог недельной серии: неделя считается успешной при adherence 100 %,
   ≥ 80 % или при выполнении «якорных» дней?
4. Насколько жёсткими могут быть правила (`enforcement = hard`): блокировать
   закрытие тренировки или только предупреждать?
5. **Решено: гибрид** (§3.10) — в MVP правила-цели с отметками, ссылка
   `mealLogId` и таблицы дневника зарезервированы. Открыто: в какой фазе
   включать дневник и где хранить базу продуктов (клиент или сервер)?
6. Сравнение программ показывать только по завершённым или и по отменённым?

**Модель и техника**

7. Ротация против дней недели: реализуем оба `scheduleKind` с самого начала
   или начинаем с `weekday`?
8. Хранить ли журнал ревизий со снимками или ограничиться номером ревизии и
   сводкой изменений (дешевле, но не даёт откат)?
9. Нужны ли разгрузочные недели (deload) как первоклассная сущность
   (`program_week` с модификатором) или как `SProgression_Rule`?
10. Несколько тренировок в один день (двухразовые) — модель это допускает
    (несколько сессий на `programDayId`), но UI и adherence нужно уточнить.
11. Цели, не связанные с телом (спорт, выносливость), — нужен ли отдельный
    тип метрики (`customMetric` с ручным вводом)?
12. Гость: программа может существовать без `userId`? Если да, нужен
    локальный профиль владельца до входа (влияет на `user_id NOT NULL`).

**Бэкенд (`docs/03`, issue 35)**

13. Что считает сервер: программу, расписание, правила, факты, статистику —
    или только программа-шаблон + факты?
14. Формат серверной статистики: совпадает с §5.1/§5.3 или это отдельные KPI?
15. Разрешает ли сервер частичную программу (без правил/целей) и правки
    структуры задним числом?
16. Единицы на сервере: кг/см (assumed по `docs/03` §4) или настраиваемые?
17. Идемпотентность записи фактов: нужен ли клиентский `clientRequestId` для
    повторной отправки тренировок после офлайна?

До ответов на вопросы 1, 7, 13 документ считается рабочим проектом: модель
устойчива к любому из вариантов, но схема и UI-потоки могут упроститься.
