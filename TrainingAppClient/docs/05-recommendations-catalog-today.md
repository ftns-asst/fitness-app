# Рекомендации, каталог программ и «Сегодня»

> Документ отвечает на продуктовый набросок из трёх частей и раскладывает его
> на проверяемые требования: **рекомендации по категориям** (питание, сон и
> прочее) с возможностью писать свои текстом; **каталог программ** с
> открытием, редактированием и статистикой; **«Сегодня»** как экран, который
> сводит активную программу, день недели и рекомендации.
> Связанные документы: `02-program-model.md` (модель программы, правила,
> статистика), `04-roadmap.md` (срезы и issues),
> `fitness-assistant-frontend-design.md` (спецификация экранов).
>
> Документ проектный: разделы 4–6 фиксируют решения, которые ещё не приняты,
> открытые вопросы собраны в §7.

## 1. Что уже есть в модели (точка отсчёта)

Прежде чем расширять, зафиксируем фактическое состояние — часть требований
уже покрыта, и дублировать её не нужно.

| Требование | Текущее состояние | Где |
|---|---|---|
| Рекомендации с категориями | `ERule_Category`: `nutrition`, `training`, `recovery`, `lifestyle`, `technique` | `Program_Model.h`, `02` §3.6 |
| Питание: белки | `ERule_Metric::ProteinGrams` + `ERule_Display_Unit::G` / `GPerKg` | там же |
| Питание: углеводы, жиры | **нет** метрик, есть только `CaloriesKcal` | §2.1 |
| Сон | `ERule_Metric::SleepHours`, `code = sleep`, категория `recovery` | `02` §3.6 |
| Свои рекомендации текстом | **нет**: `SProgram_Rule.Note` есть, но `CHECK` требует хотя бы одну цель | §2.2 |
| Каталог программ | **нет**: репозиторий умеет только `Get_Active_Program_Id` | `Program_Repository.h` |
| Открыть/редактировать программу | экраны `ProgramOverviewPage`, `ProgramEditPage` есть, но работают с фиксированным `u1` | §2.3 |
| Статистика программы | `Avm_Program_Stats`, `ProgramStatsPage` — есть | §2.4 |
| «Сегодня»: день, программа, тренировка/отдых | `TodayPage` есть, но читает `MockCatalog`, а не SQLite | §2.5 |

Вывод: **модель правил расширяется точечно, но три вещи отсутствуют
принципиально** — углеводы/жиры, текстовые рекомендации без числовой цели и
выборка списка программ. Каждая требует миграции схемы, а не только UI.

## 2. Разбор пробелов

### 2.1. Питание ограничено белками и калориями

`ERule_Metric` содержит `ProteinGrams` и `CaloriesKcal`, но не содержит
углеводов и жиров. Продуктовое требование «белки, углеводы, жиры и т. д.»
моделью не выражается: калории — это сумма, а не отдельные макросы, поэтому
пользователь не может поставить цель по углеводам и не может увидеть её
выполнение.

Единицы измерения переиспользуемы: `G` подходит для всех трёх макросов,
`GPerKg` — для белков и жиров. Нужны только значения перечисления.

### 2.2. Текстовая рекомендация невозможна принципиально

`SProgram_Rule.Note` — это **пояснение** к измеримому правилу («источник:
тренер»), а не самостоятельная рекомендация. Таблица `program_rules`
заканчивается ограничением:

```sql
CHECK (target_min IS NOT NULL OR target_max IS NOT NULL OR target_exact IS NOT NULL)
```

То есть правило без числовой цели база не примет, а `Note` без цели не
создаётся. Форма «пей 2 литра воды» возможна (метрика + `targetMin`),
а форма «не есть после 20:00» — нет: у неё нечего измерить, а другого
механизма для текста модель не предлагает.

### 2.3. Каталога программ нет

Репозиторий программ умеет отвечать только на вопрос «какая программа
активна» (`Get_Active_Program_Id`). Списка программ пользователя — активных,
черновиков, завершённых, архивных — нет ни в репозитории, ни во
`ViewModel`, ни на экране. `Avm_Program` читает одну активную программу, а
создаёт новую с нуля, не показывая результат в списке.

Это же объясняет, почему созданная программа «не появляется» нигде: у экрана
нет списка, в который её можно было бы попасть.

### 2.4. Статистика привязана к экрану, а не к программе

`Avm_Program_Stats` и `ProgramStatsPage` существуют и работают, но открываются
из обзора одной программы. Для каталога нужно то же для **любой** программы
из списка, включая завершённую, — то есть параметризация по `programId`, а не
только по активной.

### 2.5. «Сегодня» не связан с программой

`TodayViewModel.qml` — единственный оставшийся экран вкладок на mock:
`readonly property var plan: MockCatalog.todayPlan`. Названия программы, её
цели и рекомендаций там нет. При этом `Avm_Program` уже отдаёт активную
программу и её расписание, а `Avm_Program_Rules` — правила с состоянием за
сегодня. То есть **данные для «Сегодня» в C++ есть**, не хватает
ViewModel-агрегата и экрана.

## 3. Целевой вид

### 3.1. Рекомендации: категории

Категории остаются теми же, что в модели, но состав каждой явным образом
закрепляется за экраном:

| Категория (UI) | enum | Метрики | Типовые рекомендации |
|---|---|---|---|
| Питание | `nutrition` | `proteinGrams`, `carbsGrams`, `fatGrams`, `caloriesKcal`, `waterMl` | белок 1,8 г/кг, углеводы 4 г/кг, жиры 1 г/кг, вода 30 мл/кг, калории |
| Сон | `recovery` | `sleepHours` | сон 7–9 ч |
| Восстановление | `recovery` | `restHoursBetweenSessions` | отдых ≥ 24 ч между силовыми |
| Тренировка | `training` | `maxRpe` | RPE не выше 8 |
| Образ жизни | `lifestyle` | `stepCount`, `alcoholUnits` | 8 000 шагов, алкоголь |
| Техника | `technique` | `custom` | текстовые заметки о технике |
| Другое | `custom` | `custom` | всё, что не попало выше |

Ключевое решение: **`recovery` показывается как «Сон» и «Восстановление»**, а
`lifestyle` и `custom` — как «Образ жизни» и «Другое». Новые категории в enum
для этого не нужны, UI разделяет существующие; значение в enum добавляется
только вместе с новым типом проверки.

### 3.2. Рекомендации: два вида

| Вид | Что это | Пример | Проверка |
|---|---|---|---|
| Измеримая | метрика + числовая цель + единица | «Белок не ниже 130 г» | отметка `done` / `failed`, adherence |
| Текстовая | категория + заголовок + текст | «Спи в одно время — цикл сдвигается на час» | не проверяется, только показ |

Текстовая рекомендация — **не отдельная сущность**: она лежит в той же
таблице `program_rules` с признаком «цели нет». Так она попадает в каталог
программы, удаляется вместе с остальными правилами, переживает ревизии и не
заводит вторую таблицу с собственным жизненным циклом.

Отличить вид можно по наличию цели, без новой колонки: у измеримого правила
заполнено хотя бы одно из `target_min/target_max/target_exact`, у текстового —
ни одно. Метрика текстового правила — `custom`.

### 3.3. Каталог программ

Список программ пользователя с группировкой по состоянию:

| Группа | Состояния | Действия в строке |
|---|---|---|
| Активная | `active` | Открыть · Статистика · Редактировать · Пауза |
| Черновики | `draft` | Продолжить · Удалить |
| Завершённые | `completed` | Открыть · Статистика |
| Архив | `cancelled`, `archived` | Открыть (read-only) · Статистика |

Карточка строки: название, цель, срок, прогресс недель, число тренировок и
выполненных дней. Сортировка — по дате обновления; в группе «Активная» всегда
ровно одна строка (инвариант «одна активная программа», `02` §3.1).

Из каталога доступны: **открыть** (обзор программы), **редактировать**
(редактор расписания и дня), **посмотреть статистику** (KPI, adherence,
прогресс целей и правил, замеры).

### 3.4. «Сегодня»

Порядок блоков сверху вниз:

1. **Дата и день недели** — «Понедельник, 14 сентября», день недели выделен.
2. **Название текущей программы** — «Сила 12 недель», цель и прогресс недель;
   переход в обзор программы.
3. **Сегодня** — тренировка (название дня, упражнения, кнопка «Начать») либо
   отдых/кардио/мобилити с понятным заголовком вида дня.
4. **Рекомендации** — сгруппированные по категориям из §3.1, с отметками дня.

Пустые состояния: нет программы → предложение создать или взять из каталога;
программа есть, но день отдыха → блок рекомендаций без блока тренировки;
рекомендаций нет → блок не показывается вовсе.

## 4. Решения, которые надо принять

| # | Вопрос | Варианты | Предлагаемый | Почему |
|---|---|---|---|---|
| R1 | Как хранить текстовую рекомендацию | ослабить `CHECK` в `program_rules` / отдельная таблица `program_advice` | ослабить `CHECK` | одна сущность, один жизненный цикл, один экран; вторая таблица заводит две подсистемы ради текста |
| R2 | Чем отличать текстовое от измеримого | новая колонка `rule_kind` / по наличию цели | по наличию цели | производное значение не может разойтись с данными; проверка — одна функция |
| R3 | Углеводы и жиры — новые значения enum | `CarbsGrams` / `FatGrams` в `ERule_Metric` | добавить | без них требование по КБЖУ не выражается вообще; миграция CHECK-проверки нужна в любом случае |
| R4 | Питание как одна категория или три | одна `nutrition` / `nutrition` + подгруппы | одна категория, подгруппы в UI | три enum-категории ломают фильтр и отчёты по правилам; экран всё равно группирует по подкатегории |
| R5 | Текстовая рекомендация влияет на adherence | да / нет | нет | у неё нет значения, нечего сравнивать; adherence остаётся по измеримым |
| R6 | Каталог: одна программа или список | список / одна | список | требование «программа появляется в каталоге» невыполнимо без выборки |
| R7 | Редактирование завершённой программы | разрешить / только чтение | только чтение | `02` §3.1: read-only состояния структуру не меняют |

## 6. Критерии готовности срезов

Общие gates — из `04-roadmap.md` §2. Дополнительно для каждого среза:

- **45**: правило по углеводам и по жирам создаётся, сохраняется и читается
  обратно без потери; тест на конверсию новых значений enum в строку и обратно.
- **46**: текстовая рекомендация сохраняется без числовой цели и читается
  обратно; измеримое правило по-прежнему отвергается без цели; adherence не
  меняется от текстовой рекомендации.
- **47**: список содержит программы всех состояний; активная ровно одна;
  удаление черновика убирает его из списка.
- **48**: любая программа из списка открывается, редактируется и даёт
  статистику; для `completed`/`archived` структура не редактируется.
- **49**: «Сегодня» показывает дату, название активной программы, вид дня и
  упражнения либо отдых; рекомендации сгруппированы по категориям; поведение
  при отсутствии программы определено.
- **50**: расчёт возвращает четыре величины и основание; каждый коэффициент
  активности имеет имя и закреплён тестом; результат **предлагается** и не
  записывается в цели без действия пользователя; без возраста и активности
  расчёт не запускается, а не подставляет значения по умолчанию.
- **51**: повторный ввод веса в тот же день обновляет запись, а не создаёт
  вторую; сохранение замера меняет `Body_Weight_Latest_Kg` и дельту в
  статистике; повторная отметка не увеличивает их число.
- **52**: ползунок выдаёт только значения, кратные шагу инвентаря; переход
  60 → 62,5 → 65 достигается одним касанием; текстовый ввод остаётся
  доступным; тоннаж и рабочий вес на экране совпадают со значениями,
  посчитанными из подходов.

## 7. Открытые вопросы

1. **Текстовые рекомендации — только свои или импортируемые?** Если программа
   берётся из каталога, полезно ли её создатель оставлять свои заметки для
   тех, кто возьмёт программу? От этого зависит, показывать ли их на экране
   каталога.
2. **Порядок правил внутри категории.** Сортировать по типовому коду, по дате
   добавления или дать пользователю менять вручную? Для ручного порядка
   нужна колонка `sort_order` в `program_rules`.
3. **Длинный текст.** Нужен ли многострочный ввод с ограничением по длине и
   показ полным текстом, или достаточно одной строки с обрезкой?
4. **Макросы по весу — решено.** Авторасчёт КБЖУ есть, но запускается
   **отдельной кнопкой**, а не автоматически при каждом замере. Разбор — §9.
5. **Дневник питания — решён частично.** Таблица `nutrition_entries` уже есть в
   схеме, но кода, который её читает, нет. Ввод значений на главной (срез 51)
   использует `rule_checkins`, а не дневник; когда включать дневник — §10.4.
6. **Сколько ввода нужно на главной?** Достаточно веса и отметок, или сразу
   обхваты и объёмы? От этого зависит, сколько полей в первом экране ввода и
   не станет ли главная слишком длинной.
7. **Объёмы — решено.** Это обхваты тела: `body_measurements` и
   `SMeasurement_Deltas` уже умеют их хранить и считать дельты, нужен только
   экран ввода (§11.1). Тоннаж и рабочий вес считаются из подходов, вводить
   их отдельно не нужно (§11.2); удобный ввод веса — ползунок, дизайн которого
   уже описан в issue 11, но кода нет (§11.3).
8. **Возраст и активность.** Добавлять их в `users`/профиль (миграция) или
   спросить один раз при первом расчёте и хранить локально? От этого зависит,
   поедет ли расчёт на другую платформу.
9. **Шаг ввода по инвентарю.** Задаётся ли шаг на уровне упражнения (штанга —
   2,5 кг, гантели — 2 кг, блок — 5 кг) или единым шагом 2,5 кг для всего?
   Единый шаг проще, но даст невозможные веса для гантелей.
10. **Частота замера обхватов.** Раз в неделю, раз в две недели или «когда
   пользователь решит»? Схема это не проверяет, а от ответа зависит, какие
   подсказки даёт экран.

## 9. Авторасчёт КБЖУ по кнопке

### 9.1. Что уже есть в коде

Проверка репозитория показала:

| Что | Состояние |
|---|---|
| Таблица `nutrition_entries` | ✅ **есть** в схеме v2: `protein_g`, `fat_g`, `carbs_g`, `calories_kcal`, `meal_type`, `portion_grams` |
| Таблица `nutrition_day_totals` | ✅ есть: суточные итоги по тем же четырём величинам |
| Код, который их читает | ❌ **нет ни одного обращения** к `nutrition_entries` / `nutrition_day_totals` во всём `src` |
| Расчёт БЖР (Mifflin, Harris-Benedict, Katch-McArdle) | ❌ нет; поиск по `Bmr`/`Tdee`/`Mifflin`/`Macro` пуст |
| Поля для расчёта | ⚠️ `SUsers_Profile` = пол, рост, вес. **Нет возраста и нет уровня активности**, без которых БЖР и TDEE не считаются |

Последний пункт — блокирующий. Формула БЖР требует возраст, TDEE — уровень
активности. Сейчас их нет ни в профиле, ни в `profile_local`, ни в
`users` — это **миграция схемы профиля**, а не только доменный расчёт.

### 9.2. Почему кнопка, а не автоматически

Решение зафиксировано: авторасчёт запускается **отдельной кнопкой** во всех
случаях. Причины, которые видны из модели:

1. **Цель не должна молчать.** При изменении веса цель молча поедет
   (§7 вопрос 4). Кнопка делает пересчёт **видимым действием**: пользователь
   сам решает, что вес изменился достаточно.
2. **Активность меняется не по замеру.** Частота тренировок и образ жизни не
   измеряются автоматически, авторасчёт по весу был бы фиктивной точностью.
3. **Расчёт — производная величина.** Его нельзя писать в `goal_targets` без
   ручной отметки о том, что он посчитан: иначе непонятно, откуда взялось
   число и пересчитывать ли его.

### 9.3. Где живёт расчёт

| Слой | Что появляется |
|---|---|
| Схема | `birth_date`, `activity_level` (миграция v5) и результат расчёта (`macro_*`, миграция v6) в `profile_local`; без первых двух расчёт не запускается |
| Домен | `AsMacro_Calculator`: BMR (Mifflin–St Jeor) → TDEE с коэффициентом активности → белки/жиры/углеводы по цели программы и дефициту |
| Домен | Расчёт возвращает **предложение**, а не записывает цель: `SMacro_Suggestion` с четырьмя величинами и основанием («по весу 82 кг, дефицит 15 %») |
| Presentation | `AsMacro_Calculator::Suggest()` в QML; кнопка «Рассчитать» и предпросмотр результата |
| UI | Кнопка в редакторе правил рядом с метриками питания; результат показывается **до применения** |

Две опции дефицита: `maintain` (TDEE), `lose` (TDEE − 15 %), `gain`
(TDEE + 10 %). Коэффициенты активности — **константы с именами**, а не
магические числа в формуле; тест фиксирует каждое значение, иначе формулу
невозможно улучшить незаметно для пользователя.

### 9.4. Где показываются рекомендации по КБЖУ

Расчёт даёт **цели**, а не факт. Показывать их надо в двух разных местах, и
перепутать их — источник главной путаницы:

| Экран | Что показывается | Источник |
|---|---|---|
| Редактор правил | предложение от расчёта → можно принять как правило | `SMacro_Suggestion` |
| «Сегодня», блок «Сколько мне есть» | **числа расчёта** (калорийность и Б/Ж/У) и кнопка «Пересчитать»: расчёт сделан вручную и хранится; построчный показ «цель против факта» появится вместе с метриками питания (45) | `profile_local.macro_*` (миграция v6) |
| Статистика программы | средние факты за период и цель | `SProgram_Stats` (уже есть `Average_Protein_Grams_Per_Day`) |

Поля для углеводов и жиров в `SProgram_Stats` отсутствуют — там есть только
белок, сон, вода и шаги. Их нужно добавить в том же срезе, что и сами
метрики (45), иначе «выполнено» по КБЖУ нечем показать.

## 10. Ввод текущих значений на главной

### 10.1. Что уже есть

| Что | Состояние |
|---|---|
| `body_measurements` | ✅ вес и 5 обхватов, `UNIQUE (user_id, date)` — одна запись на день |
| `AMeasurement_Repository` | ✅ `Find_Measurement`, `Save_Measurement`, `Load_Range`, `Load_Latest` |
| Замеры в статистике | ✅ `Body_Weight_Start/Latest/Delta_Kg`, `Measurement_Deltas` — уже считаются |
| Отметки правил | ✅ `rule_checkins` + `Save_Checkin` в `Avm_Program_Rules` |
| Экран ввода | ❌ на `TodayPage` только два блока: список упражнений и ещё одна карточка |

Важно: **замеры уже учитываются статистикой**. Поэтому «ввод текущих
значений» — это не новая сущность, а экран для существующей. Но замеры и
отметки правил — разные вещи, и их нельзя смешивать (см. §10.2).

### 10.2. Два разных ввода — и почему

| Ввод | Таблица | Что записывает | Кто читает |
|---|---|---|---|
| **Замеры тела** | `body_measurements` | вес, обхваты | статистика программы: старт/последний/дельта |
| **Отметки рекомендаций** | `rule_checkins` | сон, вода, шаги, белок | adherence правил и средние значения |

Разделение существенное: замер — это **факт тела** (можно измерить только
один раз в день, `UNIQUE`), отметка — это **оценка пользователем** (можно
отмечать несколько раз, есть `state`). Ввод объёмов и веса в одну форму с
отметками сна смешал бы две сущности и сломало бы статистику: `body_measurements`
не переживёт несколько записей в день, а `rule_checkins` не умеет хранить
обхваты.

### 10.3. Состав блока на главной

Один экран ввода, две секции:

**Секция «Замеры»** — вес (обязательное), обхваты (необязательные, сворачиваются).
Сохраняется в `body_measurements` за текущую дату. Повторный ввод в тот же
день — обновление той же строки, а не новая запись.

**Секция «Рекомендации на сегодня»** — те же поля, что и блок рекомендаций из
§3.4 (сон, вода, шаги, белок), с отметками в `rule_checkins`. Значения
подставляются из `Avm_Program_Rules`.

Кнопка «Рассчитать КБЖУ» (§9) стоит в блоке рекомендаций по питанию, а не в
секции замеров: расчёт — это про цели, ввод — про факты.

### 10.4. Почему ввод идёт в `rule_checkins`, а не в дневник

`nutrition_entries` в схеме есть и подходит точнее (белки/жиры/углеводы по
приёмам пищи, штрихкоды), но это **дневник питания** — отдельный продуктовый
модуль с каталогом продуктов и историей блюд (`02` §3.10). Ввод «сколько
белка я съел сегодня» на главной к дневнику не относится: это оценка по
рекомендации, и ей место в `rule_checkins`.

Перевод отметки питания на `computedFromLog` — осознанный отдельный шаг, когда
дневник будет включён. Пока источник `selfReport`, что уже поддерживается
моделью.

### 10.5. Влияние на статистику

Ввод обязан влиять на статистику без ручного пересчёта:

| Действие пользователя | Что происходит автоматически |
|---|---|
| сохранил вес | инвалидируется кэш `program_stats`: `Body_Weight_Latest_Kg`, дельта, `Measurement_Deltas`, прогресс целей по весу |
| сохранил отметку сна/воды/белка | инвалидируется `Rule_Adherence_Percent` и средние значения по этому правилу |
| сохранил отметку несколько раз за день | перезапись записи той же пары `ruleId + date`, без роста числа отметок |

Обе инвалидации идут через существующий механизм `AStats_Repository`
(§5.4 `02-program-model.md`), новый код инвалидации не нужен — нужен вызов
существующего из точки записи.

## 11. Обхваты тела и ручной ввод рабочего веса

### 11.1. Обхваты тела: хранилище уже готово

Требование «ввод текущих значений веса, объёмов и т. д» в части обхватов
моделью покрыто целиком, ничего new не нужно:

| Что | Состояние |
|---|---|
| `body_measurements` | ✅ `weight_kg`, `chest_cm`, `waist_cm`, `hip_cm`, `arm_cm`, `thigh_cm`, `UNIQUE (user_id, date)` |
| `EMeasurement_Key` | ✅ `chest`, `waist`, `hip`, `arm`, `thigh` |
| `AMeasurement_Repository` | ✅ `Find_Measurement`, `Save_Measurement`, `Load_Range`, `Load_Latest` |
| Дельты обхватов в статистике | ✅ `SMeasurement_Deltas` (`Start_Cm` → `Latest_Cm` → `Delta_Cm`) |
| Цель по обхвату | ✅ `EGoal_Metric::MeasurementCm` + `measurement_key` в `goal_targets` |
| Экран ввода | ❌ не существует |

Нужен только экран (§10.3) и правило частоты замера. Обхваты измеряют раз в
1–2 недели, а вес — каждый день, поэтому **замер обхвата при уже
существующем весе за сегодня может обновить только обхват**, не затирая вес:
это поддержано схемой, где каждое поле — отдельная пара «значение + признак».

### 11.2. Рабочий вес: считается из подходов, а не вводится отдельно

Здесь важно не создать лишнюю сущность. Рабочий вес **не надо вводить
руками как отдельную величину** — он выводится из фактов подходов:

| Величина | Как считается | Где |
|---|---|---|
| Рабочий вес упражнения | максимум `weight_kg` среди засчитанных подходов | `SExercise_Strength.Working_Weight_Kg` — **уже считается** |
| e1RM | `weight × (1 + reps / 30)` | `Progress_Support::E1rm` — **уже есть** |
| Тоннаж | `Σ (weight × reps)` по засчитанным подходам | `Set_Tonnage` — **уже есть** |
| Тоннаж программы | сумма по сессиям, есть в статистике | `SProgram_Stats.Tonnage_Kg` |

То есть «ручной ввод рабочего веса» — это **ручной ввод подходов**, из
которых вес получается сам. Отдельное поле «рабочий вес» было бы вторым
источником правды о том же числе и разошлось бы с подходами при первом же
изменении. Если пользователь хочет зафиксировать рекорд вне тренировки,
это отдельная задача и отдельная таблица, а не поле в секции замеров.

### 11.3. Ползунок для веса: дизайн уже есть, кода нет

Issue 11 в `04-roadmap.md` уже описывает нужный контрол:

> `WeightRuler.qml` (шаг 2,5 кг, метки каждые 10 кг, акцентное деление),
> `RepsWheel.qml` (до 10 000, accent-рамка), `RpeSelector.qml` (5–10);
> подход ≤ 3 касаний

Проверка репозитория: **ни одного из трёх компонентов нет**, `Slider`,
`SpinBox` и `Stepper` в QML не используются вообще — весь ввод идёт через
`AppTextField`. Так что требование «удобно, в виде ползунков» упирается в
отсутствующий компонент, а не в правку существующего.

Почему ползунок, а не текстовое поле, здесь оправдан:

| Свойство ползунка | Следствие для UX |
|---|---|
| фиксированный шаг 2,5 кг | вводятся только реальные веса: штанга всегда собирается из дисков по 1,25 кг, 80 кг — кратно 2,5 |
| вес монотонно растёт | ползунок не даёт случайно поставить 7,3 кг |
| видно соседние значения | переход 60 → 62,5 → 65 — одно движение, без набора текста |

Ограничения, которые надо учесть при реализации:

1. **Шаг зависит от инвентаря.** Для гантелей нужны пары по 2 кг (или 1 кг),
   для штанги 2,5 кг, для блока 5 кг. Один шаг на всё упражнение даст
   невозможные значения для гантелей — шаг задаётся на уровне упражнения.
2. **Диапазон.** 500–300 кг для штанги, 2–100 кг для гантелей, ползунок
   ниже 20 кг делается отдельным коротким (линейная шкала на 0–500 превращает
   мелкий вес в две точки).
3. **Ползунок не исключает текст.** Нужен прямой ввод для дробных значений и
   для нестандартного инвентаря; ползунок — основной путь, поле — запасной.
4. **Тактильный отклик** на каждое деление: без него попасть в 62,5 на
   100-шаговом диапазоне невозможно.

### 11.4. Что показывать для тоннажа

Тоннаж уже считается, но в интерфейсе есть только текстовые упоминания в
спецификации профиля («Тоннаж/нед. 14,8 т»). Блок «Объёмы» на главной:

| Показатель | Источник | Период |
|---|---|---|
| Тоннаж недели | `SWeek_Aggregate.Tonnage_Kg` | текущая неделя |
| Тоннаж программы | `SProgram_Stats.Tonnage_Kg` | с начала программы |
| Рабочий вес по упражнениям | `SExercise_Strength` | лучший за период |
| Дельта обхватов | `SMeasurement_Deltas` | старт → последний замер |

Тоннаж — **производная величина от подходов**, поэтому в блоке ввода на
главной его нет: он появляется в блоке показа, рядом с рабочим весом, и
источник у них общий (факты тренировок).
