# 07 — UI модуля «Программы тренировок»: спецификация элементов

Статус: зафиксировано (срез W, issue 41–44 + S1/S2).
Источник истины: код `qml/Pages/Program/*`, `qml/Components/*`, `qml/Theme/*`.
Макеты: `docs/mockups-programs/` (HTML, те же токены и копирайт).
Открытых долгов по модулю нет. Последний закрыт миграцией v4: `Kg` в
`ERule_Display_Unit`, из-за отсутствия которого метрика «вес тела» была
недоступна в форме своего правила.
Долги по токенам `warning`/`borderSubtle` и по карте недели закрыты (§3.1).

## 0. Назначение

Единый исчерпывающий перечень экранов, компонентов, состояний, текстов и
токенов модуля «Программы». Правило ведения: **любый новый UI-элемент сначала
фиксируем здесь (раздел 13 — чек-лист), затем добавляем в QML и в макеты**.
Если элемент есть в коде, но нет в этом документе — документ устарел, и это
ошибка ведения, а не повод «потом дописать».

## 2. Карта навигации

```
Вкладка «Планы» (PlansPage)
  └─ кнопка «Открыть» («Моя программа») → myProgramRequested
       └─ ProgramCatalogPage  (StackView push; поверх вкладок, таб-бара НЕТ)
            ├─ пусто/CTA «Создать программу» → createRequested → ProgramEditPage (programId="")
            ├─ тап по карточке (вся строка)   → openRequested   → ProgramOverviewPage
            ├─ «Настроить»                    → editRequested   → ProgramEditPage
            └─ «Статистика»                   → statsRequested  → ProgramStatsPage

ProgramOverviewPage (вход и по --screen/program-overview; programId="" → активная)
  ├─ «Создать программу» (нет программы)     → createRequested → ProgramEditPage
  ├─ «Настроить программу» (скрыта у read-only) → editRequested → ProgramEditPage
  ├─ «Правила и отметки»                     → rulesRequested  → ProgramRulesPage
  └─ «Статистика программы»                  → statsRequested  → ProgramStatsPage

ProgramEditPage (programId — правка существующей, пусто — создание)
  ├─ тап DayTile на карте недели      → dayRequested(weekday, kind) → ProgramDayPage
  ├─ «Создать программу» → created(id, false, paused?) → обзор созданной программы (replace) + тост
  ├─ «Сохранить изменения» → created(id, true, paused?) → назад + тост
  └─ BackBar «Назад» → назад

ProgramDayPage: «Готово»/BackBar → назад в редактор.
ProgramRulesPage / ProgramStatsPage: только BackBar «Назад».
```

Правила навигации:
1. Все экраны модуля открываются **поверх вкладок** → обязательный BackBar
   «← Назад» (первым элементом колонки).
2. Стек: каталог → обзор → редактор → день; назад всегда возвращает на шаг.
3. Полная история переходов на каждую вкладку (AppShell.tabHistory): переход
   на другую вкладку снимает поток, но помнит цепочку; возврат на вкладку
   восстанавливает ВСЮ цепочку одним push (страницы сами загружают свои данные
   при создании), «назад» из восстановленного экрана не ведёт в корень.
   Повторный тап по своей вкладке — сброс к её корню (нативная конвенция);
   сохранение программы заменяет редактор обзором и в стеке, и в истории.
4. Сигналы экранов обрабатывает `AppShell.qml` (push компонентов, `--screen`
   маршруты `program-catalog` и т.д.).
5. Сохранение из редактора **включает** программу, и по §2.3 активная программа
   у пользователя одна: прежняя уходит в паузу, а `created(...)` несёт третий
   признак `paused?`. Тексты сообщений (`Demo.notify`):
   «Программа создана» / «Программа создана, прежняя — на паузе» /
   «Изменения сохранены» / «Изменения сохранены, прежняя программа — на паузе».
   Молчаливая смена активной программы выглядела бы как её потеря.
6. Инструментов дизайн-ревью в интерфейсе нет (ни кнопки, ни панели с
   переключателями акцента, темы и рамки телефона): экраны открываются
   `--screen`, вкладки — `--tab`, рамка — `--frame`, частота кадров измеряется
   `--fps`; максимальная частота экрана на Android запрашивается при каждом
   запуске (`preferredDisplayModeId` — точный режим панели). Кнопка
   «Dev» рядом с заголовком экрана читалась как настройка продукта, а не как
   инструмент разработчика.
7. Жест и колесо по «пустой» области вокруг контента листают страницу
   (`DragToScroll`). На широком экране контент живёт в центрированной колонке
   (`Theme.contentMaxWidth`) или в рамке телефона, и вокруг остаётся место,
   которое странице не принадлежит: раньше жест по нему пропадал, и до
   прокрутки приходилось тянуться в центр. Нажатия страницы, кнопок и ползунков
   при этом остаются за страницей.
8. Физика флика — токены, а не дефолты Flickable: `Theme.flickMaxVelocity`
   (2500 px/s) и `Theme.flickDeceleration` (1200 px/s², чуть ниже дефолтных
   1500 — выбег дольше, список «докатывается», но лёгкий флик не уносит всю
   страницу). Значения — логические пиксели (dp) и на плотность экрана **не
   умножаются**: одновременное масштабирование скорости и декелерации
   увеличивает путь выбега во столько же раз (v²/2a). Страница скроллится
   строго вертикально (`flickableDirection`), а позиции контента выровнены
   по целым пикселям (`pixelAligned`): дробные координаты заставляют GPU
   сэмплировать текст по нецелым позициям на каждом кадре и просаживают
   частоту на мобильных GPU (наблюдалось 120 → ~86 fps при скролле).
9. Счётчик кадров включается в «Профиль → Параметры» (`FpsOverlay` поверх
   экрана, токен `Theme.fpsCounter`): плашка «59.8 fps · 120 Гц» — фактическая
   частота рядом с герцовкой панели, которую знает окно (`Screen.refreshRate`).
   Панель 90/120 Гц при вдвое меньших fps означает, что окно не попало в
   высокий режим (запрос `preferredDisplayModeId` из main.cpp не сработал либо
   система экономит батарею). Подложка тёмная полупрозрачная — плашка лежит
   поверх контента любого цвета.

~~Долг~~ **Закрыто (срез W, коммит не сделан):** ряд недели переведён на `DayTile`
(§4) в обзоре и редакторе. Было: `Flow` из `DayMapCell` (2 колонки <600 px,

читать по диагонали, а «какой сегодня» не было видно без чтения подписей. Стало:
семь отдельных плиток в одну линию, зазор `itemGap`, своя рамка и радиус у
каждой.

Детали реализации, которые стоит знать при доработке:

- `DayMapCell.qml` удалён, компонент называется `DayTile.qml`; имя файла
  перечислено явно в `CMakeLists.txt` (строка 161) — после переименования
  генерация падает с «Cannot find source file», файл надо править там же.
- Ширина плитки считается от ширины страницы, а не от ширины `Row`: на момент
  создания делегата ширина ряда ещё не посчитана и плитки получают ноль. То же
  ограничение, из-за которого в коде раньше был `Flow`.
- В обзоре «сегодня» берётся из роли `isToday` (`Build_Week_Slots` считает её
  по локальной дате устройства). В редакторе такой роли у `program_days` нет —
  отметки там нет, это осознанно: редактор правит структуру, а не показывает
  текущий день.
- Скругление у `Rectangle` задаётся `border.radius` и без рамки не рисуется —
  поэтому у черты «сегодня» скругления нет (на 3 px оно и не видно), а у
  залитой плитки `border.color: "transparent"`, иначе серая обводка поверх
  тона делала плитку вклеенной.
- Аудит вёрстки (`--diag`) прогнан на 360/390/480: семь плиток помещаются без
  горизонтальной прокрутки. `ui_smoke_program-*` — 30 тестов зелёные.

## 4. Каталог компонентов (qml/Components)

Компонент — это контракт: свойства + сигналы. Макеты в `mocks-programs`
воспроизводят именно эти контракты. Новый компонент обязан попасть в
`QML_FILES` модуля (`CMakeLists.txt`): список явный, и без строки в нём сборка
падает на «`X` is not a type» — ошибка всплывает только при запуске, потому что
разметка грузится во время выполнения.

| 3 | Шаг формы | колонка `customFormZone`: плитки метрик, цель, название, превью, действия; заголовок и подпись экрана меняются на «Своё правило» / «… · добавится в программу» | `customFormOpen == true` |

| 4 | CTA | primary в `footer`: «Готово · N правил» / «Готово» (`chosenCount`) | всегда |

**Витрина, а не список.** Шесть пресетов полноширинными карточками с кнопкой
«Добавить» занимали шесть строк экрана: каталог вытеснял «своё правило» за
пределы экрана, хотя подбор из витрины — быстрый путь, а не единственный. Плитка
в две колонки отдаёт выбор одним движением (тап по всей плитке), а категория в
ней — цветной точкой.

**Одно условие вместо двух порогов.** «Не ниже» и «Не выше» рядом читались как
два правила, и выбор между ними не был виден: правило и его отметка устроены как
одна связка «условие + значение». В модель по-прежнему уходит один порог
(`min`, `max` или `exact`) — форма лишь перестала спрашивать недосказанное.

**Число выбранного — привязка, а не вызов.** `chosenCount` читает `count` модели
правил; вызов `rowCount()` внутри привязки зависимости не создаёт, и счётчик
остался бы нулём навсегда (то же правило, что у групп правил на экране отметок).

**Метрика задаёт единицу и периодичность сама.** Таблица живёт в C++
(`Program_Rows::Build_Metric_Catalog`), а форма спрашивает только «что измеряем» и
«сколько». Проверка `Is_Unit_Valid_For_Metric()` читает ту же таблицу: без неё
форма позволила бы создать «белок в мл» — правило, которое проходит всю
валидацию и не значит ничего. Форма цели тоже берётся оттуда (`allowsMin`,
`allowsMax`, `allowsExact`): «ровно 8 RPE» бессмысленно, у нагрузки осмысленна
только граница сверху.

Категория правила выводится из метрики (`Category_For_Metric`), а не спрашивается:
спросить отдельно значило бы спрашивать то, что уже известно.

**`BodyWeightKg` в каталоге метрик — закрыто миграцией v4.** Раньше в
`ERule_Display_Unit` не было килограммов, и в `CHECK display_unit` схемы их не
было тоже: подставить «g» значило бы создать правило «вес не ниже 75 g». Теперь
`kg` добавлено в enum, в `Rule_Display_Unit_Texts`, в оба `CHECK` таблицы
`program_rules` и в словарь подписей (`unitLabel`), а метрика «Вес тела» введена
в каталог с формой цели «ровно» (`allowsExact`): диапазон для веса не осмыслен.

Рекомендация текстом создаётся формой в редакторе (§5.3, зона 7a), а не здесь:
у неё нет метрики и цели, только текст.

Подпись цели и единицы переводятся в разметке (`targetText`, `unitLabel`): модель
отдаёт машинные значения (`g`, `ml`, `count`), и в подписи они читались бы как
технический сбой.

Закрыт и последний пункт макета: **форма своего правила** внесена на этот же
экран (`objectName: customRuleForm`) — метрика и единица выбираются из каталога
метрик (`Build_Metric_Catalog`, `Is_Unit_Valid_For_Metric`), условие — из
допустимых метрикой (`allowsMin`/`allowsMax`/`allowsExact`), порог — ползунком с
диапазоном метрики, а превью показывает строку до сохранения.

**«Другое» — переключатель вида правила.** `SegmentedControl` «Измеримое /
Другое» (`objectName: ruleKindSelector`) меняет состав формы: в «Другом»
измеримая часть скрыта (метрика и порог там не «необязательны», а невозможны),
текст становится главным полем (`AppTextArea`, `objectName: ruleAdviceText`), а
добавление уходит в `addAdvice(title, text)`, а не в `addCustomRule`. Раньше
«Другое» существовало только фильтром категорий: создать такое правило здесь
было нечем, и путь лежал через редактор (§5.3, зона 7a).

**Долг по «Другое» — закрыт на уровне модели.** Раньше категория «Другое» не
имела смысла: `CHECK` в `program_rules` требовал измеримую цель у любого
правила, и текстовое правило без числа отвергалось. Теперь цель требуется либо
измеримая, либо текстовая — и текст должен быть содержательным:

| Слой | Правило | Где |
|---|---|---|
| Схема (v3) | `CHECK (target_min IS NOT NULL OR target_max IS NOT NULL OR target_exact IS NOT NULL OR (category = 'other' AND note IS NOT NULL AND TRIM(note) != ''))` | `Create_Program_Rules_Table` |
| Домен | `ERule_Category::Other` → `'other'` в `Rule_Category_Texts`; `ERule_Kind` + `Get_Rule_Kind()` + `Has_Advice_Text()` — вид правила выводится из наличия цели, а не из категории | `Program_Model.h` / `.cpp` |
| Движок | рекомендация не измерима: `Evaluate_Value` отказывает, `Compute_Rule_Stats` даёт пустую сводку, adherence программы не меняется | `Rule_Engine.cpp` |
| Репозиторий | `Validate_Rules()` через `Get_Rule_Kind()` — тот же инвариант с внятным сообщением вместо `FOREIGN KEY constraint failed` | `Rule_Repository.cpp` |

Против лазейки: пустой текст (`NULL` и строка из пробелов) не проходит, поэтому
«Другое» нельзя превратить в способ завести правило вообще без содержания.
Покрыто `acceptsAdviceRuleWithoutTarget`, `keepsMeasurableRuleTargetRequired`,
`rejectsRuleWithoutTargetNorText`, `replaceRulesAcceptsAdviceWithoutTarget`,
`replaceRulesRejectsAdviceWithoutText`, `loadRulesKeepsAdviceText`,
`migratesWithExistingRules`, `adviceRuleHasNoVerdictByValue`,
`adviceCheckinsDoNotAffectAdherence`, `ruleKindFollowsTargetPresence`,
`adviceTextMustHaveNonSpaceCharacter`.

Остаток долга по «Другому» закрыт: экран выбора правил (§5.7) внесён вместе с
переключателем вида правила, форма рекомендации есть и в редакторе (§5.3, зона 7a),
у рекомендаций в списке нет кнопок отметки. Покрыто
`test_adviceModeSendsTextRule`, `test_adviceModeKeepsFormAfterFailure`,
`test_adviceModeResetsOnOpen`, `test_advicePreviewShowsTitleAndText`.

## 8. Правила взаимодействия

1. **CTA никогда не disabled.** Кнопка активна всегда и под ней caption
   перечисляет, чего не хватает (`missingHint`). Молчаливый disabled запрещён.
2. **Ошибка видима и персистентна.** `Set_Error` обязан эмитить `changed()`,
   иначе QML-баннер не обновится (корневая причина «кнопка ничего не делает»).
   Техническая причина (`errorDetail`) показывается второй строкой.
3. **Удаление всегда возможно** (цель, правило, упражнение) — иначе ошибку
   нельзя исправить.
4. **Тап по карточке = открыть**, кнопки внутри = действия; зона тапа — вся
   карточка (`TapHandler` вне `AppButton`).
5. **Минимум касания 44 px**, кнопка ≥88 px по ширине; primary-CTA — 56 px.
6. **Окно отметок крутится по кругу** Неделя→Месяц→Квартал (7/30/90).
7. **Подтверждения-диалоги в модуле не используются** (удаление мгновенное,
   с отменой через пересоздание/повтор); `Demo.notify` — только вне модуля.
8. **Системная «назад» = BackBar** (BackHandler/BackRouter).
9. Отметку нельзя поставить чужой сессией: computed-правила без кнопок.

## 9. Адаптивность и доступность

- База — 390 dp; диапазон 360…480 без горизонтального скролла.
- `contentMaxWidth: 480` — на десктопе контент центрируется, не растягивается.
- Карта недели: **всегда 7 плиток в одну линию**, ширина каждой считается от
  ширины страницы (`(screenWidth − screenPadding*2 − itemGap*6) / 7`), а не от
  контейнера — на момент создания делегата ширина контейнера не посчитана.
  Перенос сетки 2/3 колонки больше не применяется: он делал неделю неделей
  «по диагонали». На 360 dp семь плиток помещаются (проверено в макете: зазор
  4 px, подпись дня 11 px); при нехватке места уменьшаются зазор и шрифт, но
  не количество плиток.
- `MetricCard.value` — `HorizontalFit` c floor 16 px: длинное число не вылезает.
- Перенос текста: у всех длинных подписей `wrapMode: WordWrap` +
  `Layout.minimumWidth: 0` (иначе неявная ширина выталкивает ряд).
- Контраст: textPrimary на surface ≥ 7:1 (light); muted — только для
  заголовков/декора, не для критичных текстов.
- Цвет несёт смысл (§5.5 design-doc): warning — «не заполнен», negative —
  провал, accent — успех; цвет никогда не единственный сигнал — рядом текст.
- Фокус/ошибка поля — рамка 2 px (не только цвет — толщина).

## 10. Тема и i18n

- Light/Dark: `Theme.darkMode`; все цвета — только через токены (§3.1).
  Тени рисуются лишь в light (`elevated: !darkMode`).
- Переключаемый акцент `accentIndex` 0…3 (Синий/Бирюзовый/Красно-оранжевый/
  Фиолетовый) — макеты показывают дефолтный синий.
- Выбор акцента и темы — настройка пользователя, а не инструмент ревью: блок
  «Оформление» (`AppearanceCard`) в разделе «Параметры» профиля, экран
  `--screen profile-settings`. Инструментов дизайн-ревью в UI нет: экраны и
  рамку телефона открывают ключи командной строки (`--screen`, `--tab`,
  `--frame`) — рядом с настройками пользователя они выглядели бы частью
  продукта. Значения пишутся в те же токены `Theme`, поэтому смена применяется
  без перезапуска.
- Все видимые строки — `qsTr()`; дни недели ISO 1…7 (Пн…Вс / полные имена);
  единицы: «нед.», «кг», «%», «т». Формат дат: ISO в данных (YYYY-MM-DD),
  «3 ноября 2026» в UI.
